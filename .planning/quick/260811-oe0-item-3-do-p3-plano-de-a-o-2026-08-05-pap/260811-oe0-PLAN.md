<objective>
Item 3 of the 2026-08-05 Juliano action plan's P3 ("novo papel de acesso Editor", locked in `260811-lp5-CONTEXT.md` item 3, discussed in full in `260811-oe0-CONTEXT.md`, researched exhaustively in `260811-oe0-RESEARCH.md`) — the most security-sensitive item in this series, because it extends this project's role/RLS model for the first time since Phase 5. Adds a fourth `public.user_role` value, `'editor'`: an account that sees ONLY the cards where it is `media_assignee_id` ("Designer/Mídia", shipped by quick task 260811-n0i), across every client (cross-client by construction, never client-wide), can edit that card's description and toggle its checklist items, can read (never write) its Drive attachments, and can never advance stage, create a card, or (re)assign anyone to anything.

Purpose: today "who actually does the design/media work" has no first-class account in this system — they either share a PM's login (defeating per-account audit trail and the project's own "structural, not filter" isolation principle) or work outside the platform entirely. This gives that role a real, narrowly-scoped account.

Output: two migrations in strict order (`0030` — the bare `ALTER TYPE ... ADD VALUE`, nothing else, per Postgres 55P04; `0031` — every RLS policy/helper/trigger/CASE-branch that uses the new value, plus a new nullable `cards.due_date` so the Editor's queue has something real to order by), two new pgTAP files, a dedicated Editor-only Server Action whose `.update()` payload is structurally incapable of touching `stage`/`assignee_id`/`media_assignee_id`/`channel`/`due_date`, PM/Admin-facing Editor provisioning (mirrors `createClientLogin` but with no `clientId` — an Editor has no single owning client), routing (`/editor`), a cross-client queue UI ordered by due date, and the PM/Admin-side wiring that makes an Editor account actually assignable as a card's Designer/Mídia (a real gap found during planning — see Task 5).

**A gap found during planning, not in `260811-lp5-CONTEXT.md`/`260811-oe0-CONTEXT.md`/`260811-oe0-RESEARCH.md`, and structurally necessary for this feature to work at all:** `enforce_card_assignee_membership()` (migrations `0017`/`0029`) today accepts a `media_assignee_id` ONLY if it is a member of the target client's `public.pm_clients` roster. An Editor account is deliberately never given a `pm_clients` row (it is not scoped to one client — `260811-oe0-RESEARCH.md` Section 5 point 3). Without extending this trigger, a PM/Admin could never actually assign an Editor to a card through the UI at all — the entire feature would be unreachable. Task 1 fixes this as part of migration `0031`, and Task 2's pgTAP file `0017_editor_provisioning_membership_test.sql` proves it. Likewise, the existing Designer/Mídia picker in `app/pm/board/board-panel.tsx` only ever lists `pmRoster` (client-scoped PMs, via `listClientPmRoster`) — without Task 5, no Editor account would ever appear as a selectable option even after the RLS/trigger fix. Both are addressed below; neither is scope creep — they are load-bearing plumbing for the locked decision in `260811-oe0-CONTEXT.md`.

**Deliberate deviation from `260811-oe0-RESEARCH.md`'s suggested skeleton, documented here:** no standalone `is_editor()` helper (mirroring `is_admin()`) is created. Every Editor-inclusive RLS branch below scopes directly by `media_assignee_id = (select auth.uid())` — eligibility for WHO may ever become a `media_assignee_id` is fully decided at INSERT/UPDATE time by `enforce_card_assignee_membership()`, so no policy in this plan ever needs to re-derive "is the caller an editor" as a separate check. A standalone `is_editor()` would have zero call site in this plan and be dead code.

**Checker revision (blocking FAIL closed by this update):** widening `cards_update_scoped` to include `media_assignee_id = auth.uid()` (Task 1, migration `0031`) is exactly right for `updateCardDescriptionAsEditor` (Task 3) -- but that same RLS policy was, before this revision, the ONLY authorization boundary for the three PM/Admin-facing Server Actions already living in `app/pm/board/actions.ts` (`updateCardDetails`, `advanceStage`, `moveCard`), none of which perform their own role check. Because Next.js Server Actions are resolved by their own `Next-Action` reference, not by which page rendered them, an authenticated Editor could otherwise invoke any of the three directly on a card where they are `media_assignee_id`, and RLS would permit the write -- silently breaking this plan's own locked must-have that an Editor can never advance stage, reassign, or edit Canal/Prazo/Designer-Mídia "estruturalmente, não só por convenção". Task 8 (new) closes this by applying the exact app-layer authorization pattern this codebase already established for `forceAdvanceOverride` (`lib/actions/card-overrides.ts`) and `createClientRecord` (`lib/actions/clients.ts`) to all three actions.

      -- exists()) -- an Editor is deliberately never given a pm_clients row
      -- (it is not scoped to one client), so without this second branch no
      -- Editor could ever be assigned to a card at all, making the whole

          else 'pending'
        end,
        coalesce((new.raw_user_meta_data->>'must_change_password')::boolean, false),
        (new.raw_user_meta_data->>'client_id')::uuid
      );
      return new;
    end;
    $$;

    --    dueDate field at all.
    -- ===========================================================================
    alter table public.cards

    create index idx_cards_due_date on public.cards (due_date);
