<objective>
Item 4 of the 2026-08-05 Juliano action plan's P3 ("segundo campo de atribuição no card", discussed and locked in `260811-lp5-CONTEXT.md`): give every content card a SECOND, purely informational assignment field -- e.g. "Designer/Mídia" -- alongside (never replacing) the existing "Responsável" (`assignee_id`, D-19, shipped in 03-07). Per the locked decision, this field carries NO gating logic whatsoever: it never blocks checklist completion, never blocks stage advance, never blocks drag-and-drop. It is read-only metadata on the card, exactly like `assignee_id` already is today, just a second one.

Purpose: Juliano's team splits work by role on the same card -- one PM owns "Responsável" (overall ownership), but who actually does the design/media work is a separate, equally real assignment that today has no home on the card and lives only in someone's head or a side channel. This gives it a first-class, always-visible field without inventing any new authorization rule, new role, or new state machine.

Output: migration `0029_cards_media_assignee.sql` (nullable `media_assignee_id` FK to `public.profiles`, `on delete set null`, plus an extension of the EXISTING `enforce_card_assignee_membership()` trigger function so an out-of-roster media assignee is rejected the same way an out-of-roster Responsável already is -- via `CREATE OR REPLACE`, not a second trigger), a new pgTAP file `0015_cards_media_assignee_membership_test.sql` proving that extension, `mediaAssigneeId` added to `createCardSchema` (optional) and `updateCardDetailsSchema` (nullable) in `lib/validation/cards.ts`, `createCard`/`updateCardDetails` persisting it in `app/pm/board/actions.ts`, `page.tsx` selecting/typing it and folding its ids into the existing `resolvePmNames` batch, and `board-panel.tsx` exposing it end-to-end: a "Designer/Mídia" field on card creation (mirroring the "Responsável" Select exactly, hidden for `card_type: "package"` per D-02), an edit field in the card detail dialog (sharing the existing "Salvar alterações" button, no new button), and a plain-text meta-line segment on every card that has one set (mirroring the existing "Responsável: {email}" segment, NOT a badge).

**Deliberate scope boundaries, both Claude's Discretion per `260811-lp5-CONTEXT.md` Item 4, documented here rather than left implicit:**
1. **No board-level filter, no badge.** Item 1 (channel, 260811-m0t) got both a badge and a board filter because `260811-lp5-CONTEXT.md`'s own Item 1 discretion note explicitly asked "badge? filtro? os dois?". Item 4's discretion note only asks "aparece no board/filtros?" -- and Juliano's own decision text calls this field "puramente informativo," the same wording used for "não afeta checklist, não afeta avanço de estágio." A plain meta-line segment (matching Responsável's existing treatment) is the literal analog the decision asks for; a badge or filter would be new UI surface the decision never asked for. If a filter/badge is wanted later, it is a small additive follow-up, not a scope cut of this task.
2. **Single field, not a list.** Mirrors "Responsável" (`assignee_id`) exactly, which is also a single optional FK, not an array. The decision's own wording ("mais uma pessoa marcada no card") is singular.
3. **The `cards_assignee_membership_trg` trigger IS extended to cover this new field, not left unenforced.** "Puramente informativo" describes the ABSENCE of workflow gating (checklist/stage/drag-and-drop) -- it says nothing about referential integrity. Letting the UI silently offer a name that is not actually on the client's PM roster would be a real data-quality bug (the same class of problem D-19 already prevents for Responsável), not a gate. The extension uses a DISTINCT exception token (`media_assignee_not_on_roster`, never a substring of the existing `assignee_not_assigned_to_client`) so the two violations produce distinct, correct Portuguese messages instead of being silently conflated.
4. **`media_assignee_id` is OPTIONAL/nullable, not required.** This is the direct, explicit lesson from item 1's checker-caught blocker (a required `channel` field forced updating all 3 `createCard` call sites, and one was missed). Since Responsável (`assignee_id`) itself is already optional and this field is explicitly "informational" with no workflow role, making it required would be an unjustified, undiscussed behavior change. Every `createCard` call site (`board-panel.tsx`'s `CreateCardDialog.onSubmit`/`handlePasteImport`, `chat-panel.tsx`'s `handleSendToKanban`) needs ZERO changes to keep compiling -- confirmed by grep during planning (see `<baseline>`).
</objective>

```sql
-- Quick task 260811-n0i: Item 4 of the 2026-08-05 Juliano action plan's P3
-- ("segundo campo de atribuicao no card", 260811-lp5-CONTEXT.md Item 4
-- decision) -- a SECOND, purely informative assignment field on
-- public.cards, e.g. "Designer/Midia", alongside (never replacing) the
-- existing assignee_id/"Responsavel" field from
-- 0017_cards_description_assignee.sql.
--
-- Explicitly NO gating logic: this column never blocks checklist
-- completion, stage advance, or drag-and-drop -- it is read-only metadata
-- surfaced on the card, same as assignee_id already is.
--
-- Column name chosen (Claude's Discretion per 260811-lp5-CONTEXT.md, Item
-- 4): media_assignee_id -- matches the action plan's own example
-- ("Designer/Midia") more literally than a generic "secondary_assignee_id"
-- would.
--
-- RLS is already enabled on public.cards (0015_cards.sql). ADD COLUMN does
-- not disable it, and cards_select_scoped/cards_insert_scoped/
-- cards_update_scoped are row-level with no column list, so they
-- automatically cover this new column exactly like every other column on
-- this table -- same precedent as 0025_clients_tag.sql/
-- 0027_clients_briefing_text.sql/0028_cards_channel.sql. No new policy, no
-- new grant.
--
-- Membership enforcement: extended, not skipped. "Purely informative" (no
-- checklist/stage gating) describes the ABSENCE of workflow gating -- it
-- says nothing about referential integrity. This column still identifies a
-- real person who must actually be on the client's team, the exact same
-- real-world constraint D-19 already enforces for assignee_id. So
-- enforce_card_assignee_membership() (0017) is extended below (CREATE OR
-- REPLACE, same function/trigger names -- cards_assignee_membership_trg
-- keeps firing BEFORE INSERT OR UPDATE only, never DELETE, so it can never
-- obstruct the D-15 compensating delete in createCard) to check
-- media_assignee_id with the SAME pm_clients membership rule, using a
-- DISTINCT exception token (media_assignee_not_on_roster) so app code can
-- tell the two violations apart -- deliberately NOT a suffix/prefix of the
-- existing 'assignee_not_assigned_to_client' token, to avoid a substring
-- match accidentally conflating the two in app/pm/board/actions.ts's error
-- mapping.

alter table public.cards
  add column media_assignee_id uuid references public.profiles(id) on delete set null;

-- `on delete set null` mirrors assignee_id (0017) -- deleting a PM profile
-- must orphan this assignment too, never cascade-delete the card.
create index idx_cards_media_assignee_id on public.cards (media_assignee_id);

-- CREATE OR REPLACE keeps the exact same function name/signature/trigger --
-- only the body grows a second, independent check.
create or replace function public.enforce_card_assignee_membership()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  if new.assignee_id is not null
     and not exists (
       select 1 from public.pm_clients
       where client_id = new.client_id and pm_id = new.assignee_id
     ) then
    raise exception 'assignee_not_assigned_to_client'
      using errcode = 'check_violation';
  end if;

  -- Quick task 260811-n0i (Item 4): same membership rule, same client_id
  -- comparison, applied to the second assignment field. Distinct exception
  -- token (media_assignee_not_on_roster) -- see header comment above for
  -- why it must never be a substring of the token above.
  if new.media_assignee_id is not null
     and not exists (
       select 1 from public.pm_clients
       where client_id = new.client_id and pm_id = new.media_assignee_id
     ) then
    raise exception 'media_assignee_not_on_roster'
      using errcode = 'check_violation';
  end if;

  return new;
end;
$$;
```
