<objective>
Add a way to delete a piece (`card_type='piece'`) from inside a package's "Ver peças" dialog on `/pm/board` — the gap the developer raised during phase 3 wave 9's live checkpoint (2026-08-08): once a piece is created via "Adicionar peça" there is currently no way to remove it, even when the title was a typo.

Scope is deliberately narrow: ONLY pieces. Deleting a package or a standalone (`single`) card is explicitly out of scope for this task, even though the same mechanism could generalize later.

**Correction to the original task brief, confirmed by reading the migrations directly:** `public.cards` already HAS a DELETE RLS policy — `cards_delete_scoped` (migration `0017_cards_description_assignee.sql`), plus `grant delete on public.cards to authenticated`. It was added for `createCard`'s D-15 compensating-delete fail-safe (a card created directly in revisão interna whose checklist snapshot fails must be deleted). This policy authorizes deleting ANY `card_type` the caller can reach (admin, or `client_id in pm_assigned_clients()`) — it is not scoped by `card_type` at all, and it must stay that way, because `createCard`'s compensating delete needs to remove a `single`-type card too. **No new migration is needed and the existing policy must NOT be narrowed to `card_type='piece'`** — narrowing it would silently break the D-15 fail-safe for standalone cards created directly in a gated column. The `card_type='piece'` restriction this task requires is therefore enforced ENTIRELY at the Server Action layer (`removePiece`), the same spirit as `createPiece`'s own app-layer `card_type !== 'package'` check on its parent.

Also confirmed by reading the migrations: `card_checklist_items` (0016), `card_attachments` (0018), and `card_checklist_overrides` (0022) all declare `card_id ... references public.cards(id) on delete cascade` — deleting a piece row already cascades correctly with zero extra work.

Purpose: close a small, well-scoped UX gap without touching any existing behavior from wave 9 (03-06) or any other card mutation.
Output: `removePieceSchema` (validation), `removePiece` Server Action (mirrors `createPiece`'s RLS-re-read + type-check pattern), and a delete trigger + confirmation in `PackageRow`'s piece rows.
</objective>

**Existing DELETE RLS policy — `supabase/migrations/0017_cards_description_assignee.sql` (already applied, DO NOT edit or add a new migration):**

```
create policy "cards_delete_scoped"
on public.cards
for delete
to authenticated
using (
  (select public.is_admin())
  or client_id in (select public.pm_assigned_clients())
);

grant delete on public.cards to authenticated;
```

This is the ONLY authorization boundary at the database layer, and it deliberately does not filter by `card_type` — `removePiece` is what narrows it to pieces.

**`createPiece`'s pattern to mirror, `app/pm/board/actions.ts` (unchanged, read-only reference):**
- Re-reads the target row through the RLS-scoped client (`supabase.from("cards").select(...).eq("id", ...).single()`) before acting — never trusts a `card_type` implied by the caller.
- Rejects on the wrong type with a dedicated Portuguese error constant, returned as `{ error: string }`.
- Calls `revalidatePath("/pm/board")` on success only.
- Return type is a discriminated union (`{ success: true; cardId }` or `{ error: string }`) for `createPiece`; a plain `{ error?: string }` is the simpler pattern used by `advanceStage`/`removeAttachment` for actions with nothing to hand back on success — use that simpler shape for `removePiece`, since the UI only needs to know whether it worked.

**`removeAttachment`'s minimal RLS-only pattern, same file, for contrast — do NOT copy this one:** `removeAttachment` deletes by id with zero re-read, trusting `card_attachments_delete_scoped` alone, because there is only one type of row to delete. `removePiece` needs the extra re-read step because `cards_delete_scoped` is NOT type-scoped — this is the actual reason to follow `createPiece`'s heavier pattern instead.

**`lib/validation/cards.ts` schema conventions to match** (`createPieceSchema`, `removeAttachmentSchema` as the two closest precedents — a single-field id schema):

```
export const removeAttachmentSchema = z.object({
  attachmentId: z.string().uuid(),
});
export type RemoveAttachmentInput = z.infer<typeof removeAttachmentSchema>;
```

**`app/pm/board/board-panel.tsx` — `AttachmentRow` (lines ~589-647), the exact UI pattern to mirror for the piece delete trigger:** a `ghost`/`icon`-sized `Button` (`aria-label`, `disabled={isPending}`) as the `AlertDialogTrigger`, wrapping an `AlertDialogContent` with `AlertDialogHeader`/`AlertDialogTitle`/`AlertDialogDescription`, an `AlertDialogFooter` with `AlertDialogCancel` and a `variant="destructive"` `AlertDialogAction` that calls the mutation inside `startTransition`. All of `AlertDialog`, `AlertDialogTrigger`, `AlertDialogContent`, `AlertDialogHeader`, `AlertDialogTitle`, `AlertDialogDescription`, `AlertDialogFooter`, `AlertDialogCancel`, `AlertDialogAction` are already imported at the top of `board-panel.tsx` — no new import needed for those. `lucide-react`'s `Trash2Icon` is NOT currently imported and must be added to the existing `lucide-react` import block (alongside `PlusIcon`, `XIcon`, etc.).

**`PackageRow`'s current piece-row markup to replace, same file (~lines 1196-1208):** each piece is currently rendered as a single `<button>` wrapping BOTH the title/stage AND the (not-yet-existing) delete affordance — that is invalid, since an interactive delete button cannot nest inside another `<button>`. Restructure each piece entry into an outer `<div>` (not a button) containing: (a) an inner `<button>` for the existing click-to-open-detail behavior (title + `StatusBadge`, calling the existing `handlePieceClick`, completely unchanged behavior/signature), and (b) the new delete `AlertDialog` trigger as a sibling, not a descendant, of that inner button.
