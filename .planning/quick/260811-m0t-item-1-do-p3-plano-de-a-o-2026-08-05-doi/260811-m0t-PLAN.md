<objective>
Item 1 of the 2026-08-05 Juliano action plan's P3 ("dois canais por cliente", discussed and locked in `260811-lp5-CONTEXT.md`): give every card on the existing per-client Kanban board a "Planejamento" vs "Conteúdo" classification, WITHOUT duplicating any board/column/RLS infrastructure. This is a single new `channel` column on the existing `public.cards` table, orthogonal to `card_type` (single/package/piece, KAN-01) -- never a second board, never confused with the Pacote/Peça mechanism.

Purpose: today's board only distinguishes cards by stage (Briefing -> ... -> Agendamento) and by card_type (single post vs package of pieces). Juliano's own team runs two conceptually different tracks per client -- planning work and content-production work -- and currently has no way to tell them apart on the same board. This gives every card that label, visible as a badge and filterable, while reusing every existing structure (same table, same RLS policies, same columns, same drag-and-drop).

Output: migration `0028_cards_channel.sql`, a new `lib/cards/channel.ts` module (mirrors `lib/cards/stages.ts`'s convention), `channel` added to `createCardSchema`/`updateCardDetailsSchema`, `createCard`/`updateCardDetails` persisting it, `page.tsx` selecting/typing it, and `board-panel.tsx` exposing it end-to-end: a "Canal" field on card creation (every entry point except "Colar do chat", which defaults to Conteúdo), a persistent badge on every card and package row, an edit field in the card detail dialog to reclassify later, and a client-side board filter (Todos/Planejamento/Conteúdo). Also updates `app/pm/chat/chat-panel.tsx`'s existing "Enviar pro Kanban" button (`handleSendToKanban`, shipped in quick task 260805-fuu) to pass an explicit `channel: "conteudo"` -- a third `createCard` call site discovered during checker revision, since `channel` becomes a required field on the shared `createCardSchema`.

**Explicitly NOT touched, confirmed unnecessary:** `card_type`/`lib/cards/package-rollup.ts` (channel is orthogonal, package rollup logic stays keyed purely on pieces' stages), `createPiece` (a new piece's insert omits `channel` entirely and simply picks up the column's `DEFAULT 'conteudo'`, exactly like a pre-existing row -- no extra field, no inheritance-from-parent logic), any RLS policy or GRANT on `public.cards` (0015_cards.sql's row-level policies already cover every column, same precedent as `0025_clients_tag.sql`/`0027_clients_briefing_text.sql`), and any pgTAP test file (grepped during planning -- no existing test references a `channel` column or does full-row/`select *` equality checks on `cards`; the new column has a `DEFAULT`, so every existing fixture insert is unaffected).
</objective>
