```typescript
export async function retryTropicaliaProvisioning(clientId: string) {
  const supabase = await createClient(); // RLS-scoped -- relies on clients_update_scoped
  const { data: client, error: fetchError } = await supabase
    .from("clients").select("id, name").eq("id", clientId).single();
  if (fetchError || !client) return { error: "Cliente não encontrado." };
  if (!process.env.TROPICALIA_API_KEY) return { error: "RAG setup pendente." };
  try {
    const project = await createTropicaliaProject(client.name);
    const { error: updateError } = await supabase
      .from("clients").update({ tropicalia_project_id: project.public_id }).eq("id", clientId);
    if (updateError) return { error: "Não foi possível salvar as alterações. Verifique sua conexão e tente novamente." };
    return { success: true };
  } catch {
    return { error: "Não foi possível provisionar o projeto Tropicalia agora. O cliente foi criado normalmente — tente novamente quando quiser." };
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `updateBriefing()` Server Action | Untrusted briefing field values cross into an RLS-scoped update -- RLS is the actual enforcement layer here (not an app-layer role check), since `clients_update_scoped` already correctly scopes by `pm_assigned_clients()` |
| Browser -> `assignPms()` Server Action | Untrusted `pmIds` array crosses into a privileged, admin-only write that bypasses `pm_clients` RLS by design |
| Server Component -> Client Component (`canRetry` prop) | The only Tropicalia-key-derived signal allowed to cross into client-rendered JSX is a boolean, never the key or any string derived from it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-15 | Tampering | `updateBriefing()` accepting a raw `formData` spread that could smuggle `tropicalia_project_id`, `id`, or other unintended columns into the `.update()` call | mitigate | Only the zod-parsed `briefingSchema` fields are ever passed to `.update()`; Task 1 acceptance criteria grep-forbids any raw-formData spread pattern in the function body. |
| T-01-16 | Elevation of Privilege | A non-admin PM calling `assignPms()` directly (bypassing the UI, e.g. via devtools) to add/remove PMs on a client | mitigate | `assignPms()` re-checks `role === "admin" && status === "approved"` server-side before any `createAdminClient()` write -- the UI's `viewerIsAdmin`-gated rendering is a convenience, not the security boundary; the Server Action itself is the boundary. |
| T-01-17 | Information Disclosure | `canRetry`'s underlying `TROPICALIA_API_KEY` check leaking into the browser via an incorrectly-placed `process.env` read inside a Client Component | mitigate | `client-detail-form.tsx` never imports or reads `process.env` (Task 2 acceptance criteria grep-forbids it entirely); the boolean is computed exclusively in the Server Component wrapper. |
| T-01-18 | Elevation of Privilege | `resolvePmNames()`/an equivalent admin-client read inside the detail page being reused to fetch PM data for a `client_id` the viewer isn't authorized to see | mitigate | The detail page only ever calls these helpers with the `client_id` from the URL param AFTER the RLS-scoped `clients_select_scoped` query for that same id has already succeeded -- if RLS denies the client row, the page returns a not-found state before any admin-client read happens. |
