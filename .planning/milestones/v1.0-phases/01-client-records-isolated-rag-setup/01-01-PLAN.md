<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `/login` Server Action | Untrusted email/password input crosses into server code and then into Supabase Auth |
| `.env.local` (local filesystem) -> privileged clients | `SUPABASE_SECRET_KEY` / `SUPABASE_ACCESS_TOKEN` are read only by server-only modules (`lib/supabase/admin.ts`, the Supabase CLI) -- must never reach the browser bundle or git history |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Spoofing | `/login` credential guessing | accept | D-03 explicitly scopes this as a throwaway Phase 1-4 dev login (no forgot-password, no app-layer throttling); Supabase Auth's own built-in rate limiting on `signInWithPassword()` is the baseline protection. Full login hardening is Phase 5's (05-02) scope. |
| T-01-02 | Information Disclosure | Login error message distinguishing "email not found" vs "wrong password" | mitigate | `signIn()` returns the single generic string "E-mail ou senha incorretos." for every Supabase Auth failure -- never a different message per failure reason (Task 2 acceptance criteria). |
| T-01-03 | Tampering / Information Disclosure | `SUPABASE_SECRET_KEY` / `SUPABASE_ACCESS_TOKEN` leaking into the browser bundle or git history | mitigate | Values live only in `.env.local` (already git-ignored, confirmed in 05-01's `.gitignore`), never referenced with a `NEXT_PUBLIC_` prefix, never read from a Client Component this plan or any later one in this phase. |
| T-01-04 | Elevation of Privilege / Availability | Seeded Admin/PM rows created with the wrong role or left `status='pending'` | mitigate | Task 1 acceptance criteria explicitly require `status='approved'`, `must_change_password=false`, and the correct `role` per seeded row, verified via a direct `profiles` query before sign-off. |
| T-01-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages introduced by this plan. |
</threat_model>
