<objective>
Deliver Sub-phase 1A end to end: a real Admin or PM can create a client, have PMs linked to it, and get an isolated Tropicalia RAG project auto-provisioned -- all reachable through the client list and creation form built in this plan.

Purpose: This is the first true vertical slice of Phase 1 -- after this plan lands, a real user (Juliano or the new collaborator, logged in via Plan 01-01) can do something they could not do before: create a client record that exists as the anchor for everything downstream. It directly matches CONTEXT.md's own definition of Sub-phase 1A ("client created, PM linked, Tropicalia project auto-provisioned") and Juliano's 2026-07-11 deadline. Briefing (CLI-04) is explicitly excluded from this plan per D-07/Sub-phase 1A's own scope -- it ships in Plan 01-04.

This plan also closes a research gap not flagged in RESEARCH.md/PATTERNS.md: `profiles_select_own_or_admin` RLS (0004_rls_policies.sql) restricts a non-admin PM to reading only their OWN profile row, meaning a PM-authenticated caller cannot query the roster of other PM profiles to populate the D-13 multi-select picker, and `pm_clients_select_own_or_admin` similarly restricts a PM's visibility of `pm_clients` rows to their own `pm_id`, meaning a PM cannot resolve co-assigned PMs' names for the D-14 list badge either. Both gaps are closed the same way: a small, read-only `createAdminClient()` lookup (`listPmRoster()`, `resolvePmNames()`), scoped strictly to display purposes for clients the viewer is already RLS-authorized to see. The actual assignment WRITE stays gated by the app-layer role check already established in `createClientRecord()` -- this plan does not loosen any RLS policy.
Output: `lib/tropicalia/client.ts`, `lib/validation/clients.ts`, `lib/actions/clients.ts`, the client list at `/admin/clients` and `/pm/clients`, and the client creation form at `/admin/clients/new` and `/pm/clients/new`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `createClientRecord()` Server Action | Untrusted `name`/`pmIds` form input crosses into a privileged multi-step transaction that bypasses RLS by design |
| Server -> `api.tropicalia.dev` | Outbound call carrying `TROPICALIA_API_KEY` as a bearer token; must never leak client-side or into logs |
| `createAdminClient()` reads (`listPmRoster`, `resolvePmNames`) | Read-only privileged reads that intentionally bypass `profiles`/`pm_clients` RLS for display purposes only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-09 | Elevation of Privilege | `createClientRecord()` performing a privileged `clients`/`pm_clients` write without first verifying the caller's role/status | mitigate | App-layer authorization check (`profiles.status === "approved" && role in ("admin","pm")`) via the RLS-scoped `createClient()` happens BEFORE any `createAdminClient()` call in the function body -- this check, not RLS, is the actual security boundary for this transaction (Task 1 acceptance criteria verify ordering). |
| T-01-10 | Elevation of Privilege | A PM caller smuggling arbitrary `pmIds` (e.g. linking themselves to a colleague's future client, or listing every PM in the org) via the creation form | accept | `clientCreateSchema` validates each id is a UUID but does not restrict WHICH PMs can be selected -- consistent with D-13's plain reading ("multi-select PM picker directly on the client creation form", no role restriction stated) and RESEARCH.md Assumption A1. Risk is bounded: this only affects the client being created in this exact transaction, never an existing client's assignment (existing-client PM reassignment in Plan 01-04 IS admin-gated). |
| T-01-11 | Information Disclosure | `listPmRoster()`/`resolvePmNames()` using `createAdminClient()` to bypass `profiles`/`pm_clients` RLS, exposing PM emails to any authenticated approved PM/Admin | accept | Internal tool, small team (~10 PMs); exposure is limited to `id`+`email` of `role='pm', status='approved'` users only (never `role='client'` or pending/rejected accounts), and `resolvePmNames()` is only ever called with pm_ids already tied to a client the viewer is RLS-authorized to see via `clients_select_scoped`. No `SECURITY DEFINER` DB function is added for this -- it stays entirely in application code, auditable and easy to remove/scope-down later. |
| T-01-12 | Information Disclosure | `TROPICALIA_API_KEY` leaking to the browser bundle via a misplaced import | mitigate | `lib/tropicalia/client.ts` has no `"use client"` directive and is only ever imported by `lib/actions/clients.ts` (a `'use server'` module); env var carries no `NEXT_PUBLIC_` prefix (matches `lib/supabase/admin.ts` discipline). |
