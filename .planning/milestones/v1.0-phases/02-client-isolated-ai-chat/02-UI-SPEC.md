# Phase 2 — UI Design Contract

> Visual and interaction contract for Client-Isolated AI Chat. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Inherits and extends Phase 1's design contract (`.planning/phases/01-client-records-isolated-rag-setup/01-UI-SPEC.md`) — this phase does not re-litigate spacing/typography/color choices already locked, only adds what's new for chat.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (already initialized — `components.json` present, confirmed via `npx shadcn info`) |
| Preset | style: `new-york`, baseColor: `neutral`, cssVariables: true, rsc: true — no third-party registries (`registries: {}`) |
| Component library | Radix UI primitives via shadcn wrapper components in `components/ui/` |
| Icon library | lucide (`lucide-react`) |
| Font | System sans-serif stack only (`--font-sans` in `app/globals.css`) — no custom webfont |
| Global typography default (pre-existing, out of scope) | shadcn's `Label`, `Button`, `Badge` primitives ship a built-in 500 (medium) weight — inherited, project-wide, not counted against this phase's 2-weight budget (same carve-out as Phase 1). |

**Already installed, reuse — no new shadcn components required this phase**: `alert-dialog`, `badge`, `button`, `card`, `checkbox`, `dialog`, `form`, `input`, `label`, `select`, `separator`, `skeleton`, `sonner`, `table`, `textarea`.

- `Select` → client switcher dropdown (D-01).
- `Checkbox` → per-message "include in saved knowledge" control (D-04) — already installed from Phase 1's PM-picker use case, same visual weight/size, no restyle.
- `Textarea` → message composer input (multi-line, Enter-to-send / Shift+Enter-for-newline).
- `Skeleton` → streaming/loading placeholder before the first token of a response arrives.
- `Badge` (`variant="outline"`) → degraded-mode notice, reusing Phase 1's "RAG pendente" neutral pattern (no new hue).
- `Sonner` (toast) → save-to-knowledge success/error feedback, matching the pattern already used in `components/clients/client-access-panel.tsx`.

No `scroll-area` or `avatar` component is introduced — the message list uses a plain `overflow-y-auto` container (D-09 keeps the UI simple: no citations, no avatars, alignment alone distinguishes PM vs. AI messages).

**Established layout pattern this phase extends**: Phase 1 confirmed no sidebar/app-shell exists yet, and none should be built as a side effect of a single feature phase. Per D-01 (chat needs "a new nav pattern... not reusing the `clients/[id]` route-group convention"), this phase resolves that narrowly: a **top-of-screen sticky header row** containing the client switcher — not a persistent sidebar. This keeps the nav-pattern surface area minimal (one dropdown, one screen) rather than introducing app-shell scope Phase 1 explicitly deferred.

**Chat screen structure** (`/pm/chat`): full-height flex column, `max-w-2xl mx-auto` content width (narrower than the `max-w-3xl`/`max-w-4xl` data-table pages from Phase 1 — conversational reading width, standard chat convention):
1. Sticky header — client switcher (`Select`), full-bleed width within the container
2. Scrollable message list — `flex-1 overflow-y-auto`, newest message anchored at the bottom
3. Sticky footer — composer (`Textarea` + icon send `Button`), plus the contextual "Salvar como conhecimento" bar when ≥1 message is checked

## Visual Focal Points

| Screen | Focal Point | Rationale |
|--------|-------------|-----------|
| Chat screen (`/pm/chat`) | The client switcher (top, sticky) is the **first** focal point — before any message content is legible | CTX-02's entire success criterion is that switching client switches the whole knowledge base; cross-client leakage is the exact failure mode this phase (and Phase 1) exist to prevent. The PM must be able to confirm "which client's context am I in" before reading or sending anything — same rationale Phase 1 used to foreground "{client name}" first on the detail page. |
| Chat screen — message thread | Composer (bottom, sticky) is the secondary focal point; the scrollable message list is tertiary | Standard chat attention flow: confirm client → read latest exchange → type next message. Per-message checkboxes (D-04) and the save bar are visually subordinate (small, inline) so curation controls never compete with the primary read/write loop — they only become visually prominent once the PM has actually checked something. |

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phase 1, reused verbatim for cross-phase consistency:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, message-bubble internal icon spacing (streaming dots) |
| sm | 8px | Checkbox-to-bubble gap, timestamp-to-bubble gap, composer internal padding |
| md | 16px | Default spacing between consecutive messages, composer field padding |
| lg | 24px | Header/footer sticky-bar padding (`px-6`) |
| xl | 32px | Gap between the degraded-mode notice and the first message |
| 2xl | 48px | Space around the "no messages yet" empty state |
| 3xl | 64px | Not used on this screen (chat is edge-to-edge vertically, no page-level top padding — the sticky header sits at the viewport top) |

Exceptions: the icon-only send button and per-message checkboxes follow Phase 1's 44×44px minimum touch-target rule (padding around a 16–20px icon/control, not a break of the 4px-multiple rule). Both require an explicit `aria-label` since they carry no visible text — see Copywriting Contract.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Meta | 12px | 400 (regular) | 1.4 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

**Phase weight budget: 400 (regular) + 600 (semibold)** — unchanged from Phase 1; no third weight introduced.

Usage mapping for this phase:
- **Meta (12px/400/1.4)** — new role for this phase: message timestamps, "digitando..." / streaming state label if ever shown as text, degraded-mode notice fine print. Muted-foreground color only, never body content.
- **Body (14px/400/1.5)**: message bubble text (both PM and AI), composer input text, empty-state body copy, error text.
- **Label (14px, shadcn global default weight — pre-existing, not counted in budget)**: `Select` client-switcher label if visible, form labels.
- **Heading (20px/600/1.2)**: not used as a section title on the chat screen itself (chat has no internal sections) — reserved for any surrounding page chrome only (e.g. if the chat screen ever gains a page title above the sticky header).
- **Display (28px/600/1.2)**: not used on `/pm/chat` — this screen has no `<h1>` page title in the composer-first layout (the client switcher itself, not a heading, communicates context). If a future iteration adds a page title, it uses this role.

## Color

Palette unchanged from Phase 1 — zero-chroma neutral + one destructive red, no new hue introduced for chat.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `oklch(1 0 0)` ≈ `#FFFFFF` (`--background`) | Page background behind the message list |
| Secondary (30%) | `oklch(0.97 0 0)` ≈ `#F5F5F5` (`--card` / `--muted` / `--secondary`) | Both message bubble types (see below), sticky header/footer surfaces, degraded-mode notice background |
| Accent (10%) | `oklch(0.205 0 0)` ≈ `#262626` (`--primary`) | Reserved for: the send button ("Enviar", icon-only) and the "Salvar como conhecimento" button only — plus the default focus ring. **Not** used on message bubbles, the client switcher, checkboxes, or the streaming indicator. |
| Destructive | `oklch(0.577 0.245 27.325)` ≈ `#DC4C3F` (`--destructive`) | Destructive actions only. No destructive action exists in this phase's own scope (no delete/clear-conversation control — D-03 keeps one ongoing history with no reset UI); reserved for future reuse, same as Phase 1's note. |

Accent reserved for: send button + "Salvar como conhecimento" button + default focus ring — nothing else.

**Message bubble differentiation uses alignment + Secondary-tier surfaces, not color** — consistent with Phase 1's "no color-coding" discipline (status badges there used neutral variants + icon, not hue):
- **PM message**: right-aligned, `bg-secondary text-secondary-foreground`, rounded corners (`rounded-2xl`)
- **AI message**: left-aligned, `bg-card text-card-foreground border`, rounded corners (`rounded-2xl`)
- **Streaming (in-progress AI message)**: same AI bubble styling, with a `Skeleton`-style pulsing three-dot indicator appended at the end — no color change, no accent tint
- **Degraded-mode notice**: `Badge variant="outline"` (same pattern as Phase 1's "RAG pendente") — neutral, not a new semantic color

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA — send message | Icon-only button (lucide `SendHorizontal`), `aria-label="Enviar mensagem"` — no visible text label; Enter-to-send in the composer is the primary path, the button is the click fallback |
| Secondary CTA — save curation | Salvar como conhecimento (appears only once ≥1 message checkbox is checked, in a sticky bar directly above the composer) |
| Client switcher placeholder | Selecionar cliente |
| Per-message checkbox (accessible name) | `aria-label="Incluir esta mensagem no conhecimento salvo"` on every message's checkbox (both PM and AI messages, per D-04) |
| Empty state — no client selected yet | Heading: Nenhum cliente selecionado · Body: Selecione um cliente acima para começar a conversar. |
| Empty state — client selected, no messages yet | Heading: Nenhuma mensagem ainda · Body: Faça uma pergunta sobre {client name} para começar. |
| Degraded-mode notice (D-06/D-07 — Tropicalia key absent or client unprovisioned) | Busca de contexto indisponível — respostas usam apenas o briefing do cliente. (persistent `Badge variant="outline"`, top of the message list, same neutral tone as Phase 1's "RAG pendente"; no retry button shown here — retry only applies to the client-detail RAG-provisioning flow from Phase 1, not to an individual chat turn) |
| Error — message failed to send | Não foi possível enviar sua mensagem. Verifique sua conexão e tente novamente. (inline, below the composer — matches Phase 1's server/network error tone verbatim) |
| Error — response interrupted mid-stream | A resposta foi interrompida. Tente novamente. (shown in place of the incomplete AI bubble, paired with a "Tentar novamente" text button — reuses Phase 1's RAG-retry CTA label) |
| Success — knowledge saved (toast) | Conhecimento salvo. As mensagens selecionadas foram enviadas para a base de conhecimento do cliente. |
| Error — knowledge save failed (toast) | Não foi possível salvar o conhecimento. Tente novamente. |
| Destructive confirmation | None in this phase's scope — no delete/clear-conversation action exists. Saving curated knowledge (D-05) is additive, not destructive, so it proceeds without a confirmation dialog, consistent with D-05's "no preview/edit step before confirming." |

**Out of UI-scope note**: the file-shape question for Tropicalia uploads (new `.md` per save vs. append to one running file — CONTEXT.md's Claude's Discretion item) does not change any copy or visual element above; the save button, its label, and the success/error toasts are identical regardless of which shape the technical research/planning phase resolves. No further UI decision is blocked on it.
