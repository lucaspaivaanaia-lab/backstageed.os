> Visual and interaction contract for Admin Oversight Dashboard. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Plus the project's own non-shadcn primitives: `StatusBadge` (`components/ui/status-badge.tsx`), `PageShell`/`PageTitle`/`SectionTitle`/`EmptyState` (`components/layout/page-shell.tsx`). No `Dialog`/`AlertDialog` needed — unlike `/admin/cards`, this screen has no row-level detail modal; drill-down is a page navigation (D-03), not an in-place expansion.

- `Table` → the consolidated cross-client card table (D-01) and the workload panel (D-04) — both reuse the exact `Table`/`TableHeader`/`TableBody`/`TableRow`/`TableHead`/`TableCell` set already used by `/admin/cards`.
- `StatusBadge` → the staleness/stalled flag (D-02, primary new visual element this phase introduces) and the per-stage count chips inside the workload panel.
- `EmptyState` → "no cards anywhere" and "filtered to zero results" states, reusing the same component `/admin/cards` already uses.

**Design decision resolving CONTEXT.md's open discretion item (screen placement):** this phase ships as a **new screen at `/admin` root**, replacing the current "Em construção" placeholder (`app/admin/page.tsx`) — not as an extension of `/admin/cards`. Rationale: `/admin/cards` already has an established, distinct purpose (CHK-04's per-card checklist/override audit trail, Dialog-based drill-in). Phase 6's job is different — triage/staleness at a glance across the whole operation, with different columns (no checklist/anexos) and a different interaction model (no Dialog, whole-row navigation instead). Overloading `/admin/cards` with both purposes would violate CONTEXT.md's explicit non-goal ("should not duplicate the existing `/admin/cards` screen's purpose... without a clear reason"). Making `/admin` the oversight dashboard also directly serves the phase goal — it becomes what Juliano sees the instant he logs in, with zero extra clicks.

## Visual Focal Points

| Screen | Focal Point | Rationale |
|--------|-------------|-----------|
| `/admin` | The staleness/stalled `StatusBadge` column (rightmost column, "Atualizado") is the **first** thing that should register — a warning/danger-toned badge should visually stand out against an otherwise neutral table | ADM-02's entire requirement is "distinguish stalled from on-track without opening each one individually" — the badge, not the row, carries that signal. Default sort (staleness descending) reinforces this: the worst offenders are always the first rows Juliano sees. |
| `/admin` — workload panel | The "Distribuição por etapa" chips (bottleneck visibility — e.g. a PM with 4 cards stuck in "Revisão interna") are the secondary focal point, below the main table | D-04's panel exists to answer "who's overloaded and where," not just "who has the most cards" — a flat count alone under-serves that. |

## Screen Layout & Component Notes

### `/admin` — Oversight Dashboard (replaces the placeholder in `app/admin/page.tsx`)

1. `PageShell` (width: `wide`, matching `/admin/cards` — data-dense screen).
2. `PageTitle` "Visão geral" — **no `action` slot** (no primary CTA this phase; see Copywriting Contract).
3. Filters row (`flex items-center gap-md`, directly under the title, same position as `/admin/cards`'s client filter):
   - Client `Select`, default value `all` ("Todos os clientes") — identical component, copy, and `?client=` query-param mechanism as `/admin/cards`.
   - PM `Select`, default value `all` ("Todos os responsáveis") — new this phase, drives `?pm=`. Resolves CONTEXT.md's open discretion item ("drill into any PM's cards"): filtering the **same** consolidated table by the Responsável column, client-side query param, **not** a second navigation target or a PM-scoped route (no PM-scoped equivalent of `/pm/board` exists or is being proposed).
4. Consolidated cross-client card table (D-01) — `Table`, directly below the filters row:
   - One row per card, **`card_type` in (`single`, `piece`) only** — packages (`card_type = 'package'`, `stage = null`) are excluded, since they have no stage value for the Etapa column (same exclusion `/pm/board` already applies when grouping by `STAGE_ORDER`).
   - Columns, left to right: **Cliente · Título · Responsável · Etapa · Atualizado**. (The four locked in D-01 — client, PM, stage, time-since-update — plus Título, since a bare stage+staleness row with no title is not actionable at a glance; card_type/channel are deliberately omitted to keep the table scannable, per CONTEXT.md's discretion note leaving this to the researcher/planner.)
   - Etapa column: `STAGE_LABELS[stage]` inside a `StatusBadge tone="neutral"` — identical rendering to `/admin/cards`'s existing Etapa column.
   - Atualizado column: the staleness badge (see "Staleness Computation" below) — this is the **only** new visual signal this phase introduces.
   - Default sort: staleness descending (oldest `updated_at` first — the most-stale card is always row 1). No user-facing sort-order control this phase (a fixed, opinionated default matching "daily glance" usage, per CONTEXT.md's discretion note) — column-header click-to-sort is not required for MVP.
   - Row interaction: whole-row click/keyboard-activate (`role="button"`, `tabIndex={0}`, `Enter`/`Space`, identical pattern to `/admin/cards`'s `CardAuditRow`) navigates via `router.push('/pm/board?client=' + card.client_id)` (D-03) — a full page navigation, **not** a Dialog. This is the one interaction-model difference from `/admin/cards`: no Dialog exists on this screen at all.
5. Workload panel (D-04) — `SectionTitle` "Carga de trabalho" + a second `Table`, below the main table on the same scrollable page (not a tab, not a second route):
   - One row per PM/Editor who currently has ≥1 active card (rows with zero active cards are omitted, not shown with a "0" — keeps the panel focused on real workload).
   - Columns: **Pessoa · Cards ativos · Distribuição por etapa**.
   - "Cards ativos" definition (exact, for planner/executor): `card_type` in (`single`, `piece`) AND `stage is not null` AND `publish_at is null` — excludes "Pronto para publicar" cards (SCH-02), since those are finished work, not open workload.
   - PM rows count by `assignee_id`; Editor rows count by `media_assignee_id` — the same combined roster shape `/pm/board`'s loader already assembles (`pmRoster` + `editorRoster` via `listClientPmRoster`/`listEditorRoster`, cross-client for this Admin-only screen).
   - "Distribuição por etapa" renders one small `StatusBadge tone="neutral"` chip per stage with count > 0 (e.g. "Briefing 2", "Produção 1", "Revisão interna 3"), space-separated with `gap-xs` — never a stage with 0 cards.

### Staleness Computation (D-02)

`daysSinceUpdate = floor((now - cards.updated_at) / 86400000)`. Three tiers, each with an exact threshold and `StatusBadge` tone — this is the phase's core new visual contract:

| Tier | Threshold | Tone | Badge copy |
|------|-----------|------|-------------|
| Fresh | `daysSinceUpdate < 3` | `neutral` | "Atualizado hoje" (0 days) / "Atualizado ontem" (1 day) / "Atualizado há {N} dias" (2 days) |
| Stalled | `3 <= daysSinceUpdate < 7` | `warning` | "Parado há {N} dias" |
| Overdue | `daysSinceUpdate >= 7` | `danger` | "Parado há {N} dias" |

Explicitly accepted tradeoff (per CONTEXT.md D-02, already surfaced to the user): `updated_at` resets on any edit, not just a stage transition — this is an approximation of "stalled," not a precise time-in-current-stage measure. No new schema/column this phase.

## Color

Palette unchanged from Phases 1–5 — the indigo-tinted neutral system + `success`/`warning`/`danger`/`info`/`neutral` `StatusBadge` tones already defined in `app/globals.css`. No new hue introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `oklch(1 0 0)` ≈ `#FFFFFF` (`--background`) | Page background, table row background |
| Secondary (30%) | `oklch(0.97 0 0)` ≈ `#F5F5F5` (`--muted` / `--card`) | Table header row, sidebar, `StatusBadge tone="neutral"` fill |
| Accent (10%) | `oklch(0.45 0.15 265)` ≈ indigo (`--primary`) | Reserved for: the active sidebar nav item ("Visão geral"), the default focus ring on `Select`/table rows. **Not** used on table rows, headers, or any badge — this screen has no primary "create/submit" action to anchor accent color to. |
| Warning | `oklch(0.52 0.12 75)` (`--warning`) | Reserved exclusively for: the "Stalled" tier staleness `StatusBadge` (3–6 days) |
| Danger/Destructive | `oklch(0.577 0.245 27.325)` ≈ `#DC4C3F` (`--destructive`) | Reserved exclusively for: the "Overdue" tier staleness `StatusBadge` (≥7 days). No other destructive-toned element this phase — there is no delete/override action on this screen. |

Accent reserved for: active sidebar item + default focus ring — nothing else. This is the leanest accent usage of any phase so far, appropriate to a pure read/triage screen with zero create/mutate actions. `StatusBadge` tones (`neutral`/`warning`/`danger`) are the separate, already-established soft-wash status system and are not counted against the 10% accent budget — same precedent as every prior phase.
