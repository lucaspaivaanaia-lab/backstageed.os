## Client Board Layout & Component Notes (`/client`)

*(New-screen detail beyond the base template's fixed sections — informs planner task-writing and executor implementation directly.)*

### Page structure
- `PageShell` (width: `default`, matching Editor's own single-column list screen — this is not a data-dense admin grid).
- `PageTitle`: **"Meu conteúdo"** (deliberately distinct from the existing "Aprovações" nav label already used at `/admin/approvals` for PM-signup approvals — a different feature entirely; reusing that label here would create real vocabulary collision for a user who is never exposed to the admin screen but whose copy might still be read by the team).
- `Tabs` (`defaultValue="queue"`): two triggers — **"Para revisar"** (`value="queue"`) and **"Histórico"** (`value="history"`). Each tab's count is shown inline in its trigger label when non-zero, e.g. `Para revisar (3)`, matching the existing "no color-coding by category, plain count communicates state" discipline (03-UI-SPEC.md's column-header precedent).

### Queue tab (stage `aprovacao_cliente`)
- Flat list of `DataCard`s, one per card (single or piece — package parents are structurally excluded by RLS since `stage = null`; a piece renders exactly like a single card, no package-grouping UI, per Phase 3's D-01/D-02 per-piece-independence precedent applied here with zero new code).
- Each `DataCard`: `title` = card title, `badge` = `StatusBadge` tone `info`, copy **"Aguardando sua revisão"**, `description` = card description (or omitted if null — never render "Sem descrição" as a title-adjacent label on a review surface, that copy is reserved for editable-field placeholders elsewhere).
- **Minimal surface only** (CONTEXT/RESEARCH discretion, resolved): title, description, attachments. No checklist state, no PM/Designer-Mídia assignee, no channel badge, no internal stage history — none of this is rendered anywhere on `/client`.
- Sorted by `created_at` ascending (oldest-waiting-first — no due_date exposed to Client, so this is the only meaningful default order).
- Empty state: see Copywriting Contract.

### History tab (stage `agendamento`, read-only)
- Same flat-list `DataCard` shape as the queue, but every card here is non-interactive (clicking still opens the detail Dialog to view content, but that Dialog renders **no** Aprovar/Solicitar ajuste actions — read-only per D-01).
- Badge: `StatusBadge` tone `success`, copy **"Aprovado"** when `publish_at` is null, or **"Pronto para publicar"** when `publish_at` is set (SCH-02) — same computed `isReadyToPublish()` predicate the PM board uses (Pattern 5, RESEARCH.md), imported once and rendered identically on both surfaces so the two screens can never disagree.
- When `publish_at` is set, the card's `meta` slot also shows the formatted date/time (`Intl.DateTimeFormat("pt-BR", { dateStyle: "medium", timeStyle: "short" })`, same formatter already used for checklist audit timestamps).
- Empty state: see Copywriting Contract.

### Card detail Dialog (Client-facing)
- Opened by clicking any `DataCard` in either tab (`DialogTrigger asChild`, identical wrapper pattern to `editor-queue-panel.tsx`).
- Contents, top to bottom:
  1. `DialogTitle` = card title.
  2. Stage-relevant `StatusBadge` (same tone/copy as the triggering `DataCard`'s badge).
  3. Description — rendered as plain read-only text (`text-body`, `whitespace-pre-wrap` matching the chat-bubble precedent from 260811-ihx), never an editable `Textarea` — the Client never edits a card's description.
  4. Attachments — read-only list, identical row shape to `EditorAttachmentRow` (label/url as an `underline` link, `target="_blank"`, `rel="noreferrer"`), only rendered if the card has at least one attachment.
  5. **Queue cards only** (`stage === 'aprovacao_cliente'`): "Sua avaliação" section — a `Textarea` (always visible, not conditionally revealed — CONTEXT's discretion point resolved in favor of the simpler single-surface option, avoiding a branching UI state) with placeholder **"Descreva o que precisa mudar (obrigatório apenas para solicitar ajuste)"**, followed by two sibling `Button`s: **"Aprovar"** (primary/default variant) and **"Solicitar ajuste"** (outline variant, `disabled` until the trimmed comment is non-empty). No `AlertDialog` on either — both are direct actions with a toast on success, mirroring "Avançar"'s own no-confirmation precedent (03-UI-SPEC.md) since neither is destructive/irreversible from the Client's own vantage point (approving is the expected path; adjusting is a normal, everyday workflow action, not data loss).
  6. **History cards only** (`stage === 'agendamento'`): no action row at all — the Dialog is purely informational (title/badge/description/attachments), confirming D-01's "read-only" requirement visually, not just at the RLS layer.
- Both actions call their own narrow Server Action (`approveCard`/`requestAdjustment`, `app/client/actions.ts`) inside a `useTransition`, disabling both buttons while pending (`isPending ? "Enviando..." : "Aprovar"` / `"Enviando..." : "Solicitar ajuste"`), and close the Dialog + `revalidatePath("/client")` on success (no client-side card removal from local state — the RSC re-read is the source of truth, same discipline as every other Server Action in this codebase).

## PM-Side Additions (`app/pm/board/board-panel.tsx`'s `CardDetailDialogBody`)

*(Two additive changes to the existing PM/Admin card detail Dialog — no restructuring of what's already there.)*

### 1. Adjustment comment (read-only, PM/Admin-visible)
- Rendered directly below the existing stage `StatusBadge`, in the same position/box style already used for the AI-validation summary block (`flex flex-col gap-2 rounded-md border p-3`) — whenever non-null, regardless of stage (a comment stays visible after the PM has read it; nothing auto-clears it except the Client's next round overwriting it, per D-02).
- Label: **"Comentário do cliente"**, body = `client_adjustment_comment` verbatim, `whitespace-pre-wrap`.
- No edit affordance — this field is Client-write-only (Pattern 2/4, RESEARCH.md); the PM never edits it directly, only reads it while revising the card's own description.

### 2. Publish date field (PM/Admin-editable, gated to `agendamento`)
- New `SectionTitle` **"Data de publicação"** + `Input type="datetime-local"` — placed directly below the existing "Prazo" field, identical shape/sizing (same `toDatetimeLocalValue`/`draftDueDate` pattern, new sibling state `draftPublishAt`).
- **Gated to render only when `card.stage === 'agendamento'`** — hidden entirely (not disabled) for every earlier stage, since the field is structurally meaningless before client approval (D-03, RESEARCH's recommended gating condition). This is the one new conditional-render branch in an otherwise unchanged Dialog.
- Included in the existing "Salvar alterações" save-state pattern (same `hasDetailChanges` dirty-check, same `updateCardDetails` Server Action call, same `CARD_DETAILS_SAVED_TOAST`/`CARD_SAVE_ERROR` copy) — **no new Server Action, no new button.** `publishAt` is simply one more field in the existing payload/schema.
- Once set, a `StatusBadge` tone `success` **"Pronto para publicar"** renders next to the stage badge at the top of the Dialog, and on the card's own `DataCard` badge slot on the board (replacing the plain stage badge for cards in `agendamento` with `publish_at` set) — using the same `isReadyToPublish()` predicate as the Client's history tab (Pattern 5).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.4 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 18px | 600 (semibold) | 1.3 |
| Display | 28px | 600 (semibold) | 1.2 |

**Phase weight budget: 400 (regular) + 600 (semibold)** — unchanged from Phases 1/2/3, no third weight introduced. (shadcn's built-in 500/medium weight on `Button`/`Tabs`/`Badge` primitives is the existing project-wide carve-out, not counted against this budget.)

Usage mapping for this phase:
- **Label (12px/400/1.4)** (`--text-meta`): tab-trigger count suffix (`(3)`), publish-date formatted display, `StatusBadge` text.
- **Body (14px/400/1.5)** (`--text-body`): card titles inside `DataCard`, Dialog description text, comment `Textarea` content and its rendered read-only counterpart, empty-state body copy, error/toast text.
- **Heading (18px/600/1.3)** (`--text-title`): `DataCard` title weight (baked into `DataCard`), Dialog title, "Sua avaliação"/"Comentário do cliente"/"Data de publicação" `SectionTitle`s.
- **Display (28px/600/1.2)** (`--text-display`): `PageTitle` "Meu conteúdo" — the only new `<h1>` this phase introduces.

## Color

Palette unchanged from Phases 1/2/3 — the indigo-tinted neutral system + one destructive red + `success`/`warning`/`info`/`neutral` `StatusBadge` tones already defined in `app/globals.css`. No new hue introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `oklch(1 0 0)` ≈ `#FFFFFF` (`--background`) | `/client` page background |
| Secondary (30%) | `oklch(0.97 0 0)` ≈ `#F5F5F5` (`--card` / `--muted` / `--secondary`) | `DataCard` surfaces, Dialog background, comment read-only block background |
| Accent (10%) | `oklch(0.45 0.15 265)` ≈ indigo (`--primary`) | Reserved for: the "Aprovar" button (primary variant), the active `Tabs` trigger indicator, the default focus ring. **Not** used on "Solicitar ajuste" (outline variant — a normal secondary action, not accent-worthy on its own), not on any `DataCard` surface, not on the comment block. |
| Destructive | `oklch(0.577 0.245 27.325)` ≈ `#DC4C3F` (`--destructive`) | **Not used this phase** — no destructive action exists on `/client` or in the PM-side additions (approve/adjust are both standard workflow actions, not deletions; see Board Layout notes for why no confirmation dialog was introduced). |

Accent reserved for: "Aprovar" button + active Tabs indicator + default focus ring — nothing else. `StatusBadge` tones (`success`/`warning`/`info`/`neutral`) are the pre-existing soft-wash system (10% opacity fills per `status-badge.tsx`) used for all status communication this phase (`Aguardando sua revisão` → `info`, `Aprovado`/`Pronto para publicar` → `success`) and are not counted against the 10% accent budget — same precedent as every prior phase.
