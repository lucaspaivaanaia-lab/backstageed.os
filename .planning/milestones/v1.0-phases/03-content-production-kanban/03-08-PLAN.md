| Boundary | Description |
|----------|-------------|
| browser drag state → `moveCard` | The card id and the target stage originate entirely in client-side drag state; both are attacker-controlled by construction |
| `evaluateMove` in the browser → `evaluateMove` on the server | Two evaluations of the same predicate; only the server one is a boundary |
| new npm dependency → the browser bundle | `@dnd-kit/*` ships to every PM's browser on the board route |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-45 | Tampering | Treating the client-side `evaluateMove` result as the gate, so anyone calling `moveCard` from the console moves a card past an incomplete checklist | mitigate | The browser call is explicitly a UX affordance; plan 03-07's `moveCard` re-reads `card_checklist_items` server-side and re-runs `evaluateMove` before any write (T-03-36). This plan adds no server logic at all |
| T-03-46 | Tampering | A malformed or spoofed `over.id` / `active.id` producing a write to an unintended stage | mitigate | `stageFromDroppableId` and `cardIdFromDraggableId` return `null` for anything not matching their namespaced prefix and, for stages, anything outside `STAGE_ORDER`; `onDragEnd` no-ops on `null`. `moveCardSchema`'s `z.enum` is the server-side equivalent |
| T-03-47 | Tampering | Optimistic UI showing a card in a column the server rejected, leaving the PM believing a blocked move succeeded | mitigate | No optimistic update is applied on a client-side rejection at all (step 6 returns before the transition).
