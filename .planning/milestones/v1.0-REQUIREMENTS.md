# Requirements: BackstageEd.OS

**Defined:** 2026-07-01
**Core Value:** Um PM consegue produzir conteúdo para um cliente específico com IA que só conhece aquele cliente (RAG isolado, zero vazamento de contexto), levar esse conteúdo do briefing até a aprovação do cliente dentro da própria plataforma, e o Juliano consegue ver o status real de qualquer card, de qualquer cliente, a qualquer momento.

## v1 Requirements

Requirements for initial release. Each maps to roadmap phases.

### Authentication & Access (AUTH)

- [x] **AUTH-01**: PM can sign up with email and password
- [x] **AUTH-02**: New PM signup requires admin approval before gaining access to the platform
- [x] **AUTH-03**: Admin can view, approve, or reject pending PM signups (rejected accounts are marked rejected, not deleted)
- [x] **AUTH-04**: Admin can assign a role (PM or Admin) to an approved PM signup
- [x] **AUTH-05**: User session persists across browser refresh
- [x] **AUTH-06**: PM can only access clients they are assigned to (enforced via Supabase RLS)
- [x] **AUTH-07**: Client can only access their own content (enforced via Supabase RLS)
- [x] **AUTH-08**: Admin can access all clients, PMs, and content
- [x] **AUTH-09**: PM can create a Client login (email + provisional password) linked to an existing client record — no self-signup or approval queue for Clients
- [x] **AUTH-10**: Client is forced to change their provisional password on first login
- [x] **AUTH-11**: PM (or Admin) can deactivate a Client's access

### Client Management (CLI)

- [x] **CLI-01**: Admin or PM can create a new client record
- [x] **CLI-02**: Admin can assign one or more PMs to a client
- [x] **CLI-03**: Each client's uploaded files (PDF/TXT/MD/DOCX) are stored as extracted text in `public.client_files`, RLS-scoped by `client_id`, isolating that client's context from all others (migrated from Tropicalia project provisioning on 2026-07-22)
- [x] **CLI-04**: PM can fill and edit a client's structured strategic briefing (objective, tone of voice, target audience, content pillars)

### Client-Isolated AI Context (CTX)

- [x] **CTX-01**: PM can chat with AI about a specific client, with context limited to that client's `client_files` rows (RLS-scoped, injected directly into the prompt)
- [x] **CTX-02**: Switching the active client in the chat switches the entire knowledge base consulted — no context bleeds from one client to another
- [x] **CTX-03**: PM can manually select a piece of a conversation to save as permanent knowledge for the client — nothing is saved automatically
- [x] **CTX-04**: Saved knowledge is written as a curated `.md` file and inserted directly as a new row in the client's `client_files` (Supabase) — no external upload endpoint
- [x] **CTX-05**: AI responses are generated via the Claude API using the client's full `client_files` content injected server-side, with the system prompt assembled server-side for tone/system-instruction control

### Content Production — Kanban (KAN)

- [x] **KAN-01**: PM can create a content card for a client, representing either a single post or a package of related pieces (e.g. a multi-post campaign)
- [x] **KAN-02**: Card moves through a defined flow: briefing → produção → revisão interna → aprovação do cliente → agendamento
- [x] **KAN-03**: PM can view all cards for a client as a Kanban board, grouped by state
- [x] **KAN-04**: When the client requests an adjustment on a card, it returns to the produção stage and must pass revisão interna again before returning to the client
- [x] **KAN-05**: PM can attach Google Drive links (image, video, PDF) to a card without needing to open Drive directly

### Review Checklist (CHK)

- [x] **CHK-01**: Admin can define a set of review checklist items required before a card can move to client approval
- [x] **CHK-02**: Checklist items can be configured differently per client
- [x] **CHK-03**: PM checks off checklist items on a card during revisão interna, and completion is tracked before the card can advance
- [x] **CHK-04**: Admin can see, per card, which checklist items were completed and when (auditability — no silently skipped steps)

### Client Approval (APR)

- [x] **APR-01**: Client can view their content organized as a board of cards ready for their review
- [x] **APR-02**: Client can approve an individual content item
- [x] **APR-03**: Client can request an adjustment on an individual content item, with a comment explaining what to change
- [x] **APR-04**: Adjustment comments are attached to the original card and visible to the PM, not lost in a separate document

### Admin Oversight (ADM)

- [x] **ADM-01**: Admin can view a consolidated status overview across all clients and PMs
- [x] **ADM-02**: Admin can identify which cards are stalled/overdue versus on track
- [x] **ADM-03**: Admin can drill into any specific client's or PM's cards for detail

### Scheduling (SCH)

- [x] **SCH-01**: Once a card is approved by the client, PM can register the agreed publish date/time on the card
- [x] **SCH-02**: A card with a registered publish date/time is marked with final status "Pronto para publicar"

## v2 Requirements

Deferred to future release. Tracked but not in current roadmap.

### Integrations

- **INTG-01**: Automatic capture of meeting transcripts via Google Calendar/Meet, feeding client context
- **INTG-02**: WhatsApp channel per PM to feed client context
- **INTG-03**: Automatic publishing via social network APIs (replacing the manual Mlabs step)

### Notifications

- **NOTF-01**: Email notification when a card is approved by the client
- **NOTF-02**: Email notification when a client requests an adjustment
- **NOTF-03**: User can configure notification preferences

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Automatic meeting transcript capture (Calendar/Meet) | Mapped as future integration — not part of the core process v1 solves |
| WhatsApp channel per PM | Mapped as future integration — deferred |
| Automatic publishing via social APIs | v1 only registers date/time and marks "ready to publish"; PM still posts manually via Mlabs |
| Email notifications | v1 is in-app only; PM and client see status changes when they access the platform |
| Self-signup without approval | Every signup (PM or Client) requires admin approval before access — no open registration |

## Outcomes

All 38 v1 requirements shipped and are live-verified against production as of 2026-08-14.

- **CLI-03 / CTX-01 / CTX-04 / CTX-05 — mechanism changed mid-milestone, requirement intent unchanged.** RAG isolation shipped as a per-client Tropicalia project in Phase 1, then migrated 2026-07-22 (quick task 260722-hnm) to direct `public.client_files` storage in Supabase with full-content injection into the system prompt — no embeddings/vector store. Driven by a Tropicalia business-model change and low real per-client file volume (~3 files). Isolation stayed structural (RLS-scoped by `client_id`) throughout; only the storage backend changed. SEED-001 (catalog/llms.txt indirection) captures the follow-up if file volume grows.
- **AUTH-06/07/08 — closed later than the rest of Phase 5, via quick tasks, not the original 05-03 plan.** The pgTAP RLS suite that proves these at the Postgres layer couldn't execute in the original sandboxed environment (no Docker). First real run (05-06) surfaced a missing `GRANT` on `public.clients`, closed by quick tasks 260716-au8/b8w/bjk (GRANT fixes on `clients`/`profiles`/`pm_clients` + an AUTH-08 fixture-count test bug) — all three requirements PASS locally as of 2026-07-16, independently confirmed the underlying gap was local-dev/CI-only (production's hosted Supabase project already had the correct grants).
- **AUTH-09/AUTH-11 (and the write-path half of AUTH-06) — a real IDOR was found and fixed before ship.** 05-VERIFICATION.md's initial pass (2026-07-14) found `createClientLogin`/`deactivateClientAccess` used the service-role client with no caller-scope check, letting any PM provision or deactivate a Client login outside their assigned clients. Closed by plan 05-05 (CR-01/CR-02): added an `is_admin()`/`pm_assigned_clients()` authorization gate in front of both actions, verified by a Docker-free automated regression test.
- **KAN-01 (package half) — delivered via a 2026-07-31 mid-execution re-scope**, not the original Phase 3 plan sequence. `card_type='package'` with independently-advancing `piece` children shipped in 03-06/03-07/03-08/03-09, alongside drag-and-drop (dnd-kit), per-column card creation, and card description/assignee fields — all added to Phase 3's scope after execution started (see ROADMAP.md's Phase 3 re-plan note).
- **No requirement was dropped or descoped.** Everything in the original 2026-07-01 v1 scope shipped, several (Editor role, workload panel, shared knowledge base, package batch-generation) arriving as post-hoc quick tasks against the 2026-08-05 stakeholder action plan rather than as roadmap phases — tracked in STATE.md's Quick Tasks Completed table.
