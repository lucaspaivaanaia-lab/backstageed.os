<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client browser → `app/client/actions.ts` | Untrusted input (`cardId`, free-text `comment`) crosses here on every `approveCard`/`requestAdjustment` call — Next.js Server Actions are reachable directly (not bound to the page that renders their trigger), so this file's own checks are load-bearing, not just UX |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05 | Tampering | `approveCard`/`requestAdjustment` writing a forbidden column (stage other than the two legal targets, or any other `cards` column) | mitigate | Both actions write EXCLUSIVELY through `buildClientApprovePayload`/`buildClientAdjustPayload` (04-01) — the `.update()` call never spreads raw input; 04-01's `FORBIDDEN_KEYS` unit test enumerates `client_id`/`channel`/`assignee_id`/`media_assignee_id`/`due_date`/`publish_at` as structurally absent from both payloads |
| T-04-02b | Tampering | A Client caller bypassing the stage gate by invoking `approveCard`/`requestAdjustment` on a card not in `aprovacao_cliente` (e.g. replaying a stale `cardId` after the PM has already advanced it elsewhere) | mitigate | Server-side re-read of `stage` immediately before any write, rejecting with `WRONG_STAGE_ERROR` unless `card.stage === "aprovacao_cliente"` — never trusts a stage claim from the browser (same discipline as `advanceStage`'s own `nextStage(card.stage)` re-derivation) |
| T-04-04b | Elevation of Privilege | A deactivated Client's still-valid session invoking `approveCard`/`requestAdjustment` directly (bypassing `middleware.ts` via a raw Server Action POST) | mitigate (defense-in-depth) | `assertClientCaller` re-reads `profiles.role`/`profiles.status` on every call, independent of `middleware.ts`'s redirect gate — mirrors `assertPmOrAdminCaller`'s "fails closed on any read error" discipline exactly |
| T-04-06 | Information Disclosure | The Client's card detail Dialog rendering internal PM-coordination fields (checklist state, assignee, channel) that CONTEXT explicitly says must not leak | mitigate | UI-SPEC's minimal-surface requirement is enforced structurally by this task never importing/rendering those fields — Task 3's acceptance criteria greps for their absence |
| T-04-SC | Tampering (supply chain) | npm/pip/cargo installs | accept — not applicable | Zero new packages this phase |
</threat_model>
