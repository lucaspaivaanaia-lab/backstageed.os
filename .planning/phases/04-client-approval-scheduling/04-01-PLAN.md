<objective>
Lay the schema and pure-logic foundation Phase 4's two vertical slices (Client-facing board, Wave 2's 04-02; PM-facing publish date/comment, Wave 2's 04-03) both build on: a fourth, stage-filtered RLS branch on `public.cards`/`public.card_attachments` scoped to the Client role, two new nullable columns (`client_adjustment_comment`, `publish_at`), and the pure "RLS decides rows, a Server Action decides columns" payload builders + the "computed, never stored" publish-status predicate that downstream Server Actions/UI will call directly.

This plan also closes an app-layer authorization gap the SAME RLS widening would otherwise open: `cards_update_scoped`'s new Client branch makes six OTHER pre-existing PM/Admin Server Actions in `app/pm/board/actions.ts` (`toggleChecklistItem`, `addAttachment`, `removeAttachment`, `validateCardAgainstChecklist`, `createPiece`, `removePiece`) newly reachable by an authenticated Client caller, none of which have a role check of their own — they rely entirely on RLS having previously had no Client branch at all. This is the exact audit CONTEXT.md's `code_context` section directed ("this phase should audit whether any existing PM/Admin action's RLS scope needs a similar app-layer guard once a Client-scoped RLS branch is added to `cards_update_scoped`"), and it must land in the SAME wave as the migration, not a later one, so there is never a window where the migration is live without the guard.

A second, third-round revision closes a SEVENTH — and, per an exhaustive repo-wide sweep of every `"use server"` file touching `cards`/`card_checklist_items`/`card_attachments`, the LAST — reachable write path the same RLS widening opens: `updateCardDescriptionAsEditor` (`app/editor/actions.ts`), the Editor role's own card-description write action, has ZERO role/status check of its own today — only `if (!user)` — and relies entirely on RLS. Unlike the six actions above (which need the PM/Admin-shaped `assertPmOrAdminCaller` guard), this action's own caller is expected to be the Editor role, so it needs the INVERSE-shaped guard: reject anyone who is NOT `role='editor' && status='approved'`, including a Client whose own row would otherwise now legitimately match `cards_update_scoped`'s new Client branch. Without this guard, an authenticated Client could invoke `updateCardDescriptionAsEditor` directly on one of their own client's cards currently in `aprovacao_cliente` — the re-read would succeed (new Client SELECT branch matches) and the update would succeed (new Client UPDATE branch's `using`/`with check` both match, since the payload never touches `stage`) — overwriting `cards.description` and completely bypassing `approveCard`/`requestAdjustment`'s hardcoded payload builders (`lib/security/client-card-write-scope.ts`, Task 3). This is a genuine, live, RLS-permitted write-boundary bypass, not defense-in-depth, and — same rule as the other six — must land in the SAME wave as migration 0032. Together, Task 4 (6 actions) and Task 5 (this 7th action) close all 9 PM/Admin-shaped and 1 Editor-shaped reachable write paths this plan's own RLS widening opens; no further audit of this kind is expected for this migration.

Purpose: every mechanic this phase needs has a direct, already-verified precedent in this codebase (Editor role, `260811-oe0`/migration `0031`) — this plan reproduces that precedent for the Client role exactly, so 04-02/04-03 can be pure "wire it up" work with zero further RLS/schema design decisions.
Output: migration `0032`, pgTAP file `0018`, `lib/security/client-card-write-scope.ts` (+test), `lib/cards/publish-status.ts` (+test), an extended `lib/validation/cards.ts`, an extended `app/pm/board/actions.ts`/`lib/security/board-write-authz.ts`/`lib/security/board-write-authz.test.ts`, and a guarded `app/editor/actions.ts` backed by a new `lib/security/editor-card-write-authz.ts` (+test).

  supabase: Awaited<ReturnType<typeof createClient>>,
  userId: string
): Promise<boolean> {

From `app/editor/actions.ts` (current state today, pre-Task-5 — the entire function, no role/status check exists yet, only `if (!user)`):
```
export async function updateCardDescriptionAsEditor(
  input: UpdateCardDescriptionAsEditorInput
): Promise<UpdateCardDescriptionAsEditorResult> {
  const parsed = updateCardDescriptionAsEditorSchema.safeParse(input);
  if (!parsed.success) {
    return { error: parsed.error.issues[0]?.message ?? "Dados inválidos." };
  }

  const supabase = await createClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();
  if (!user) return { error: NOT_AUTHENTICATED_ERROR };

  // Re-read the card through RLS -- never trust that cardId is one of the
  // caller's assigned cards; cards_select_scoped's media_assignee_id
  // branch is the real boundary.
  const { data: card } = await supabase
    .from("cards")
    .select("id")
    .eq("id", parsed.data.cardId)
    .single();
  if (!card) return { error: CARD_NOT_FOUND_ERROR };

  const { error } = await supabase
    .from("cards")
    .update(buildEditorCardUpdatePayload(parsed.data.description))
    .eq("id", parsed.data.cardId);

  if (error) {
    return { error: CARD_SAVE_ERROR };
  }

  revalidatePath("/editor");
  return {};
}
```
