<objective>
Deliver the admin approval slice: a shared login that persists across refresh and routes by role, plus an admin queue where an admin sees pending PM signups (with their email) and approves (assigning PM or Admin role) or rejects each — rejection marks the row, never deletes it.

Purpose: This closes the loop opened by 01-01. 01-01 lets a PM sign up into a pending state and blocks them; this plan lets an admin actually let them in (or turn them away) and proves the role-routing established in 01-01's middleware works for a real, logged-in, role-assigned user. Session persistence (AUTH-05) falls out of the @supabase/ssr middleware wiring already built in 01-01 and is verified here through the login flow.

Output: A `/login` screen + Server Action, an `/admin/approvals` queue page + approve/reject Server Actions, and three role-scoped landing shells so routing is provably reachable for each role.

Delivers AUTH-03 (view/approve/reject pending PM signups, rejected marked not deleted), AUTH-04 (assign PM or Admin role on approval, effective next login), and AUTH-05 (session persists across refresh).
</objective>

<phase_goal>
**As a** platform admin, **I want to** see everyone who has requested PM access — including their email — and approve them with a role or reject them, **so that** only people I have vetted can log in and each of them lands in the area their role allows.
</phase_goal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> login Server Action | Untrusted email/password crosses into server code and Supabase Auth |
| Authenticated user -> profiles UPDATE | Any authenticated session could attempt to approve/reject; only RLS is_admin() + the column-immutability trigger authorize it |
| Anon/authenticated key -> profiles table | Only RLS stands between a token holder and reading/mutating profile rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Elevation of Privilege | A non-admin authenticated user calling approveSignup/rejectSignup directly | mitigate | profiles UPDATE RLS policy scoped to is_admin() (from 01-01 0004 migration) AND prevent_profile_privilege_escalation() trigger are the actual boundary; UI gating is not relied upon (Task 2 Anti-Pattern note) |
| T-01-07 | Tampering / Repudiation | rejectSignup deleting rather than marking, destroying audit trail | mitigate | rejectSignup UPDATEs status='rejected', never .delete(); verified by grep gate (Task 2) per D-05 |
| T-01-08 | Spoofing | Trusting an unverified cookie/session for the rejected-account check | mitigate | login action reads profiles after signInWithPassword and never uses getSession() for the decision (Task 1) |
| T-01-09 | Elevation of Privilege | Assigning an unexpected role value via approveSignup | mitigate | role argument validated to 'pm'\|'admin' before the UPDATE (Task 2) |
| T-01-SC | Tampering | npm installs | accept | No new packages introduced in this plan — all deps installed and audited (Approved) in 01-01's Package Legitimacy Audit; no [ASSUMED]/[SUS] packages, no blocking legitimacy checkpoint required |
</threat_model>
