<objective>
Prove — at the Postgres RLS layer, not the UI — the three data-isolation guarantees that are the highest-severity requirements of this phase: a PM only sees clients they are assigned to (AUTH-06), a Client only sees their own client's data (AUTH-07), and an admin sees everything (AUTH-08). Deliver an automated pgTAP suite that runs via `supabase test db`.

Purpose: These three requirements are explicitly non-negotiable "enforced at the data layer (RLS), not just hidden in the UI" per the phase success criteria, and RLS misconfiguration (CVE-2025-48757 class) is the single highest-severity risk in this phase. 01-VALIDATION.md classifies AUTH-06/07/08 as the only requirements in Phase 1 that get automated coverage (pgTAP) rather than manual click-through. This plan is that coverage — it turns the RLS policies already shipped in 01-01 into a regression-proof, executable proof.

Output: Four SQL files under `supabase/tests/` — a shared fixture/role-simulation helper plus one pgTAP test file per requirement — that exercise the ACTUAL `is_admin()` / `pm_assigned_clients()` helpers and `profiles`/`pm_clients`/`clients` RLS policies from 01-01's migration 0004, and pass under `supabase test db`.

Delivers AUTH-06 (PM blocked from unassigned clients at RLS), AUTH-07 (Client blocked from other clients' data at RLS), AUTH-08 (admin unrestricted by RLS). No production code or schema changes — pure test deliverables against the existing schema.
</objective>

</phase_goal>

- function public.is_admin() returns boolean — language plpgsql, stable, security definer, set search_path = '' — true when caller's profile has role='admin' AND status='approved'.
- function public.pm_assigned_clients() returns setof uuid — language plpgsql, stable, security definer — returns client_ids from pm_clients where pm_id = auth.uid().
- RLS policies on profiles (self-select OR is_admin(); admin full access), pm_clients (is_admin() OR pm_id = auth.uid()), clients (is_admin() OR id in pm_assigned_clients() OR id = own profile's client_id).

Role simulation in pgTAP against these policies (RESEARCH.md Pattern 4 / Validation Architecture, and Supabase pgTAP docs): a policy references `(select auth.uid())` — `auth.uid()` reads the `sub` claim from `current_setting('request.jwt.claims')`. To simulate a signed-in user in a test, set the GUC and the Postgres role before the assertion:
- `select set_config('request.jwt.claims', json_build_object('sub', <user_uuid>, 'role', 'authenticated')::text, true);`
- `set local role authenticated;`
- run the query, assert visible rows, then `reset role;` and clear the claim for the next actor.
