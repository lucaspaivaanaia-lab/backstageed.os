<objective>
Deliver the Client-access lifecycle slice: a PM (or Admin) provisions a Client login for an existing client record with a system-generated provisional password, that Client is forced to change the password on first login, and the PM (or Admin) can later deactivate the Client's access entirely.

Purpose: This completes Phase 1's account model. 01-01/01-02 handle PM self-signup, admin approval, and role routing; this plan adds the other half of the phase's access story per CONTEXT.md D-01/D-02/D-09/D-10 — Clients do NOT self-signup, they are PM-provisioned against an existing client record, forced to rotate the provisional password, and can be deactivated at end of contract. It exercises the service-role admin client (`lib/supabase/admin.ts`) and the `must_change_password` middleware gate — both scaffolded in 01-01 but not yet used by any real flow.

Output: A PM-facing create-client-login screen with a one-time provisional-password display and a deactivate control; a server-only Server Action pair using `auth.admin.createUser()` / `auth.admin.updateUserById()`; a forced password-change screen + Server Action that clears the `must_change_password` flag; and a server-side provisional-password generator with 12+ char entropy.

Delivers AUTH-09 (PM creates Client login linked to an existing client record, no self-signup), AUTH-10 (Client forced to change provisional password on first login), and AUTH-11 (PM/Admin can deactivate a Client's access).
</objective>

<phase_goal>
**As a** social-media PM, **I want to** create a login for my client with a provisional password they must change on first login, and be able to deactivate that access later, **so that** my client can approve their own content in the platform without self-signing-up, and I can cut off access cleanly when a contract ends.
</phase_goal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> create/deactivate Server Action | Untrusted client email + route client_id cross into server code that wields the service-role key |
| Service-role secret key -> Auth admin API | `auth.admin.*` requires the secret key, which must never reach the browser bundle |
| Client (change-password) -> profiles self-row UPDATE | The must_change_password flag clear must be a self-row update, not a lever to modify other users |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-14 | Elevation of Privilege | SUPABASE_SECRET_KEY leaking to the client bundle via the create/deactivate actions | mitigate | create/deactivate use createAdminClient() from lib/supabase/admin.ts (server-only, non-NEXT_PUBLIC_ secret) inside 'use server' files only (Task 1, Task 3) |
| T-01-15 | Spoofing | Weak/guessable provisional password reused before the forced change | mitigate | password generated server-side with 12+ char crypto entropy, never PM-typed, and forced-changed on first login (Task 1 + Task 2) |
| T-01-16 | Elevation of Privilege | A user clearing must_change_password (or changing password) for someone else | mitigate | change-password action confirms the caller via getUser() and updates only the caller's own profiles row (self-row RLS policy) (Task 2) |
