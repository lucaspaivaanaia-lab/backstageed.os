Investigation outcome (do not re-litigate): a remote/hosted execution path was considered and rejected as not drop-in viable. The test files use psql client meta-commands (`\i supabase/tests/rls_helpers.sql`) plus per-file `begin;`/`rollback;` transaction framing and the `pgtap` extension's assertion functions. The Supabase MCP `execute_sql` runs a single SQL statement over the wire and does NOT interpret `\i` or drive pgTAP's TAP harness, so it cannot run these files as-authored. Running them via a raw `psql` connection string against the hosted DB would still require a Docker/psql-capable host AND enabling `pgtap` on that project — i.e. the same human/infra step. Therefore this is a human-verify checkpoint, not an automatable executor task. This plan does NOT modify the test files; if an assertion fails at runtime, that is a bug in the test file (not in 05-01's live-verified migrations) and should be fixed in a follow-up, not here.
