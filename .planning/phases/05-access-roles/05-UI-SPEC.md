# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** This is the first frontend phase of a greenfield project. No code, no design system, and no brand assets exist yet. This spec therefore establishes **foundational** visual/tone decisions (spacing, type, color, voice) that later phases inherit, not just this phase's five screens. Later UI-SPECs should treat this file's Design System / Spacing / Typography / Color sections as the project baseline and only add phase-specific copy and components on top.

## Spacing Scale

Declared values (must be multiples of 4) — standard 8-point scale, no project precedent to override it:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, badge padding |
| sm | 8px | Compact element spacing (form label-to-input gap) |
| md | 16px | Default element spacing (form field gaps, card padding) |
| lg | 24px | Section padding (auth card padding, approval queue row padding) |
| xl | 32px | Layout gaps (space between page header and content) |
| 2xl | 48px | Major section breaks (space above/below centered auth forms) |
| 3xl | 64px | Page-level spacing (top margin on standalone auth pages) |

Exceptions: Icon-only touch targets (e.g. row action buttons in the approval queue table) use 44px minimum tap target per accessibility baseline, even though 44 isn't a multiple of 4-scale tokens — this is a touch-target accessibility floor, not a spacing token, and applies to `button` components rendered at `size="icon"`.

## Typography

No existing type scale in the codebase (greenfield). Declaring the project-wide baseline here since this is the first UI phase.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 600 (semibold) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Exactly 2 weights declared (400 regular, 600 semibold) — no light/medium/bold variants. Exactly 4 sizes declared (14/16/20/28).

Usage in this phase:
- Display (28px/600): page-level titles are minimal in this phase (auth screens are single-purpose) — used only for "Aprovações pendentes" heading on the Admin approval queue page.
- Heading (20px/600): card titles (e.g. signup form title "Criar conta", login form title "Entrar"), section titles within role-scoped landing views.
- Body (16px/400): form helper text, table cell content, pending-approval message body.
- Label (14px/600): form field labels, table column headers, badge text.

## Color

No existing palette in the codebase (greenfield). Declaring the project-wide baseline here.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (light) / `oklch(1 0 0)` — shadcn `background` token | Page background, form backgrounds |
| Secondary (30%) | `#F4F4F5` (neutral-100-ish) — shadcn `card` / `muted` tokens | Card surfaces (auth cards, approval queue table container), sidebar/nav once later phases add navigation |
| Accent (10%) | `#18181B` (neutral-900, shadcn `primary` on `new-york`/`neutral` preset) | Reserved for: primary CTA buttons only (Sign up, Log in, Approve, Save role, Change password, Create client login) — never for informational badges, links, or decorative elements |
| Destructive | `#DC2626` (shadcn default `destructive` red) | Reserved for: Reject signup button, Deactivate client access button, and their confirmation dialogs — never for warnings or non-destructive negative states |

Accent reserved for: the single primary action button per screen (Sign up / Log in / Change password / Approve+assign role / Create client login). Status badges (pending/approved/rejected) use neutral gray + destructive red only — not the accent color — to keep the 10% accent budget meaningful and avoid diluting what "accent = primary action" signals to the user.

Rationale for neutral-only palette (no brand color yet): This is an internal ops tool for a 3-person-role system (PM/Admin/Client), not a marketing surface. CLAUDE.md explicitly asks for "professional B2B internal tool, not a consumer app" tone. A neutral (black/white/gray) palette with red reserved strictly for destructive actions delivers that tone without requiring brand-color decisions this phase has no authority to make. If/when Juliano wants a brand accent color (e.g. for the Admin dashboard in Phase 6), it can be layered on top of this neutral foundation later without breaking this contract.

## Screen Inventory (phase-specific, supplementary to template)

Each screen's states are enumerated so the executor has no ambiguity about what to build.

| # | Screen | Route (per RESEARCH.md structure) | States |
|---|--------|------|--------|
| 1 | PM Signup | `/(auth)/signup` | default, submitting (button disabled + spinner), validation error (inline per-field), server error (banner, see Copywriting), success (redirect to /pending) |
| 2 | Pending Approval | `/(auth)/pending` | static only — no interactive states (per D-06, intentionally minimal, no polling/refresh affordance) |
| 3 | Login (shared) | `/(auth)/login` | default, submitting, error (see Copywriting: wrong credentials / rejected account), success (redirect by role per middleware routing table in RESEARCH.md) |
| 4 | Admin Approval Queue | `/admin/approvals` | loading (skeleton rows), populated (table: email, signup date, role selector, Aprovar/Rejeitar), empty (see Copywriting empty state), row-action-in-progress (button disabled + spinner on that row only), reject-confirmation (dialog) |
| 5 | Forced Password Change | `/(auth)/change-password` | default, submitting, validation error (password too short / mismatch confirm field), success (redirect to role-scoped landing) |
| 6 | PM creates Client login | `/pm/clients/[id]/access` (or Admin equivalent under `/admin/clients/[id]/access`) | default (empty form: email + generate/enter provisional password), submitting, error (email invalid, client already has a login — 1:1 per D-01), success (toast + display credentials once for PM to copy/share) |
| 7 | Role-scoped landing (PM) | `/pm` | populated only in this phase as a placeholder/shell — full dashboard content is out of scope (built in later phases). Must exist and be reachable to prove routing works. |
| 8 | Role-scoped landing (Client) | `/client` | same as above — placeholder shell, proves RLS + routing, not a built dashboard |
| 9 | Role-scoped landing (Admin) | `/admin` | same as above — placeholder shell; Admin's real content in this phase is the Approvals queue (#4), this is just the landing/nav shell |

**Placeholder shell content** (screens 7-9, until later phases add real content): centered card with heading "Área do {PM/Cliente/Admin}" and body text "Em construção — o conteúdo desta área será adicionado nas próximas fases." This avoids a blank white screen after login, which would look broken rather than "not yet built."

**Provisional password display (screen 6):** Shown exactly once, in a dismissible callout/card (not a toast, since it must stay visible to copy), with copy: "Senha provisória: `{password}` — anote e compartilhe com o cliente com segurança. Esta senha não será mostrada novamente." Use a `Badge` or `code`-styled inline element for the password itself (monospace) so it's visually distinguishable from surrounding text and easy to select/copy.
