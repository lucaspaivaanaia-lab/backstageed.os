<objective>
Deliver the admin approval slice on top of the foundation 05-01 already built: three role-scoped landing shells so a logged-in user of any role reaches a real page (not a 404), a one-condition middleware fix so a user landing on `/` after login is actually routed to that role root, a static `/rejected` screen so the existing middleware's rejected/deactivated redirect resolves to a real page, plus an admin queue where an admin sees every pending PM signup (with its email) and approves it (assigning PM or Admin role) or rejects it — rejection marks the row, never deletes it.

Purpose: 05-01 already shipped a working `/login` (Server Action + page), a `getUser()`-verified `middleware.ts`, and the `profiles` schema with an `email` mirror, `is_admin()` RLS policy, and privilege-escalation trigger. Gaps remain for AUTH-05 to hold end-to-end: (1) the role-root pages the middleware points at — without them a redirect would land on a 404; (2) a real redirect FROM `/` TO the role root — the login page does `router.push('/')` on success, but the current middleware role block only bounces a user who is on ANOTHER role's root (`otherRoots.some(...)`); it never checks `pathname === "/"`, so an approved user landing on `/` falls straight through to the marketing page in `app/page.tsx` instead of their role area; (3) the `/rejected` page — middleware.ts (shipped in 05-01) already redirects status='rejected' AND status='deactivated' users to `/rejected`, but no page lives there, so that redirect currently 404s; and (4) the admin approval UI that turns a `pending` PM into an `approved` one with a role. This plan builds exactly those gaps. It does NOT rebuild `/login` (it exists and works) and does NOT re-implement rejected/pending gating in the login action (middleware already does it post-login).

Note (shared infrastructure — flags 05-04): Task 1's middleware fix (redirect an authenticated, approved, non-pending/rejected/must-change user from `/` to their role root) is shared post-login routing infrastructure. 05-04-PLAN.md's forced password-change screen redirects to `/` on success and relies on this exact behavior to carry a Client on to `/client`; the checker noted 05-04 made the same (previously-false) assumption that middleware already handles `/`. That assumption becomes TRUE once this middleware fix lands, so 05-04 needs NO edit of its own for that — it is satisfied by this shared fix. (Do not modify 05-04 in this revision for the middleware fix.)

Output: three role-landing shells, a one-condition `middleware.ts` edit routing `/` → role root, a static `/rejected` screen carrying the locked rejected-account copy, an `/admin/approvals` queue page + interactive queue component + approve/reject Server Actions, and a one-line copy alignment of the existing login wrong-credentials error to the locked UI-SPEC string.

</objective>
