# Phase 3 — UI Design Contract

> Visual and interaction contract for Content Production Kanban. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Inherits and extends Phase 1's design contract (`.planning/phases/01-client-records-isolated-rag-setup/01-UI-SPEC.md`) and Phase 2's (`.planning/phases/02-client-isolated-ai-chat/02-UI-SPEC.md`) — this phase does not re-litigate spacing/typography/color choices already locked. It also builds directly on top of the 260728-uab design-system quick task (`.planning/quick/260728-uab-upgrade-de-ui-ux-sistema-de-design-de-ve/`), which formalized the persistent sidebar shell, `PageShell`/`PageTitle`/`SectionTitle`/`EmptyState`, `DataCard`, `StatusBadge`, and `ErrorBox` **explicitly as the Kanban board's foundation** — those primitives are reused as-is, not restyled.

**Already installed, reuse — no new shadcn components required this phase**: `alert-dialog`, `badge`, `button`, `card`, `checkbox`, `dialog`, `form`, `input`, `label`, `select`, `separator`, `skeleton`, `sonner`, `table`, `textarea`. Zero new shadcn installs this phase — every interaction (client switcher, card form, checklist checkboxes, Drive-link form, override confirmation) is expressible with what's already in `components/ui/`.

- `Select` → client switcher on `/pm/board`, same component/placement pattern as Phase 2's chat screen (D-10).
- `Checkbox` → checklist item toggles during revisão interna (CHK-03). Uses the shipped `data-[state=checked]:bg-primary` styling as-is — no restyle.
- `Dialog` → card detail view. Clicking a `DataCard` on the board opens its full detail (checklist, Drive attachments, "Avançar") in a `Dialog`, not a route change — keeps the board a single stateless screen, consistent with D-05's "no drag-and-drop, keep it simple" spirit. Package parent cards open a lighter Dialog listing their pieces (no checklist/attachments at the parent level — see Board Layout notes, Pitfall 4 / A3).
- `AlertDialog` → two destructive/high-consequence confirmations this phase introduces: (1) Admin's "Forçar avanço" override (D-11), (2) removing a Drive attachment link.
- `Table` → Admin's checklist-template list (`/admin/checklist-templates`) — tabular list of templates with item counts, reusing the same `Table` component already refined in 260728-uab.
- `Form` + `Input` + `Textarea` → card creation form (title, type), checklist-template item form (label), Drive-link attach form (URL + optional label).
- `Skeleton` → board column loading state while cards/checklist-completion counts are fetched.
- `Badge` (`variant="outline"`) → Drive-link type indicator inline next to each attachment (image/vídeo/PDF/outro), same neutral-outline treatment as Phase 2's degraded-mode notice.
- `StatusBadge` → **primary vehicle for all Kanban-specific status communication**: stage label chips are NOT introduced as new colored badges (the column header itself communicates stage — see Board Layout), but `StatusBadge` is used for: package rollup ("3/5 peças em revisão interna" — tone `info`), checklist completion count on a card in revisão interna ("2/4 concluídos" — tone `warning` while incomplete, `success` when all checked), and the override event marker in the audit log ("Avanço forçado" — tone `danger`).

**No new layout pattern needed.** D-10 (dedicated screen + client switcher) is confirmed to still fit: `/pm/board` follows the exact same shape as `/pm/chat` — a client `Select` at the top of the content area (inside the existing sidebar shell, not replacing it), full board below. Unlike Phase 2 (which predates the sidebar and used its own sticky header), this phase's client switcher sits inside `PageShell`, directly under `PageTitle`, since the sidebar (not a page-level sticky header) is now the app's one persistent nav element.

**Board screen structure** (`/pm/board`): `PageShell` (width: `wide`, matching data-dense admin/list screens), containing:
1. `PageTitle` "Produção" with the "Criar card" primary CTA as its `action` slot (disabled until a client is selected)
2. Client `Select` switcher, placeholder "Selecionar cliente" (same copy as Phase 2)
3. Horizontally-scrollable row of 5 fixed-width columns (280px each, `gap-lg` between columns), one per `card_stage` in enum order — see Board Layout below
4. Package parent cards render as a distinct header row **above** the column board (not inside a column — Pitfall 4), one row per active package, each showing the package title + rollup `StatusBadge` + a "Ver peças" action that opens the package Dialog

## Board Layout & Component Notes

*(Kanban-specific detail beyond the base template's fixed sections — informs planner task-writing and executor implementation directly.)*

### Columns
- 5 fixed columns, fixed order, never reordered: `briefing` → `produção` → `revisão interna` → `aprovação do cliente` → `agendamento`.
- Column width: 280px (multiple of 4, not itself a spacing-scale token — a layout constant, like the sidebar's 240px).
- Column header: stage label (Portuguese, see Copywriting) + a small count badge (`StatusBadge`, tone `neutral`) showing the number of cards in that column. No color-per-stage — consistent with this codebase's established "no color-coding by category, alignment/position communicates state" discipline (Phase 2's same rule for message bubbles).
- Cards within a column render via `DataCard`: `title` = card title, `badge` = `StatusBadge` (checklist progress, only shown for cards in `revisão interna`), `meta` = attachment count icon + package-piece indicator if applicable. No drag targets, no drop zones (D-05).
- "aprovação do cliente" and "agendamento" columns display cards read-only in this phase (no interactive card content beyond opening the detail Dialog to view state) — the PM-facing interactions Phase 4 owns for those stages are explicitly out of scope (per CONTEXT.md's Specifics section); this phase's Dialog for a card in those two stages shows the checklist audit trail (read-only) and Drive attachments, but no "Avançar" button past `agendamento` and no adjustment/approval controls.

### Package parent cards
- Rendered as a distinct header row above the 5-column board, never inside a column (Pitfall 4 — package rows have `stage = null`).
- Each package row: title + rollup `StatusBadge` (tone `info`) with copy pattern `"{checked_stage_count}/{total_pieces} em {stage_label}"` when pieces cluster in one stage, or a simple `"{total_pieces} peças"` count when pieces are spread across multiple stages (exact rollup grouping logic is a planner/executor computation detail, not a visual one — the badge itself is the only new UI surface).
- Clicking a package row opens a `Dialog` listing its pieces (title + stage `StatusBadge` per piece, no checklist/attachments at this level — package parents never have their own checklist or Drive attachments per D-02/A3). Each piece row inside this Dialog links to that piece's own detail Dialog.

### Card detail Dialog
- Opened by clicking any single/piece card on the board.
- Contents, top to bottom: title, stage `StatusBadge`, Drive attachments list (icon-by-type + label, opens in new tab — D-08), "Anexar link" form (URL input + optional label input, inline validation via the shared `isLikelyDriveLink()` check), checklist section (only rendered when `stage === 'revisão interna'` or later — read-only after revisão interna, but visible for audit per CHK-04), "Avançar" button (primary CTA, `disabled` when in revisão interna with any unchecked item — D-06), Admin-only "Forçar avanço" secondary action (only rendered for Admin role, only enabled when the gate is currently blocking — D-11).
- Checklist items render as `Checkbox` + label rows, each showing `completed_at`/`completed_by` as small `text-meta text-muted-foreground` inline text once checked (e.g. "Marcado por {name} em {date}") — this directly satisfies CHK-04's "who checked what and when" requirement inside the same UI surface, no separate audit screen needed for the per-card view.
- If an override occurred on this card, a single `StatusBadge` (tone `danger`, "Avanço forçado") appears in the checklist section header, with a small expandable note showing who/when/which items were still unchecked (reading directly from `card_checklist_overrides`) — this is the CHK-04 audit surface for the override path specifically.

### Admin checklist-template management (`/admin/checklist-templates`)
- List screen: `PageShell` (width: `default`) + `PageTitle` "Checklists" with "Criar checklist" as the `action` slot + `Table` of templates (name, item count, client-assignment count).
- Template detail/edit: form with template name (`Input`) + an ordered list of items (`label` + `Input` per row, "Adicionar item" appends a new row at the end, per-row "Remover" — no drag-to-reorder UI, matching D-05's project-wide no-DnD stance; new items append at the end of `sort_order`, no manual reordering control in this MVP slice).
- Client assignment: reuses the existing multi-select/picker pattern already established for PM-to-client assignment (per 01-CONTEXT.md's D-13 precedent cited in 03-CONTEXT.md's canonical refs) — a single-select `Select` per client row (1:1 assignment per Pattern 2 in 03-RESEARCH.md, A2), not multi-select, since each client has exactly one active template.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phases 1/2, reused verbatim:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Checkbox-to-label gap, Drive-link icon-to-label gap, `StatusBadge` icon-to-text gap |
| sm | 8px | `DataCard` internal element spacing (badge-to-title gap), checklist item row vertical gap, column-header label-to-count-badge gap |
| md | 16px | Default gap between cards within a column, column header to card list gap, Dialog section-to-section gap |
| lg | 24px | Gutter between board columns, Dialog internal padding |
| xl | 32px | Page-level padding (`--spacing-page`, matches `PageShell`), gap between client switcher and the board itself |
| 2xl | 48px | "No client selected" / "no cards yet" empty-state vertical padding (reuses `EmptyState`'s existing `py-12`) |
| 3xl | 64px | Not used on this dense, scroll-heavy board screen — reserved, same as Phase 2's note |

Exceptions: column width is a fixed 280px layout constant (still a multiple of 4, not a violation, just not itself one of the 7 spacing tokens above — same category as the sidebar's existing 240px `--spacing-sidebar`). No new touch-target exception needed — every interactive control (checkbox, icon-only remove-attachment button, "Avançar") reuses the existing `Button`/`Checkbox` size tokens already governing touch targets project-wide (`size-9` default, `size-8` icon-sm minimum).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.4 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 18px | 600 (semibold) | 1.3 |
| Display | 28px | 600 (semibold) | 1.2 |

**Phase weight budget: 400 (regular) + 600 (semibold)** — unchanged from Phases 1/2, no third weight introduced. (shadcn's built-in 500/medium weight on `Button`/`Label`/`Badge` primitives is a pre-existing, project-wide carve-out, not counted against this budget — same note as Phase 2.)

Usage mapping for this phase:
- **Label (12px/400/1.4)** (`--text-meta`): column count badges, checklist "marcado por / em" audit text, Drive-link type badge text, package rollup badge text.
- **Body (14px/400/1.5)** (`--text-body`): card titles inside `DataCard`, Dialog body content, form field text, checklist item labels, empty-state body copy, error text.
- **Heading (18px/600/1.3)** (`--text-title`): `DataCard` title weight (already baked into `DataCard`'s `font-semibold`), Dialog title, `SectionTitle` usage inside the checklist-template edit form.
- **Display (28px/600/1.2)** (`--text-display`): `PageTitle` on `/pm/board` ("Produção") and `/admin/checklist-templates` ("Checklists") — the only two new `<h1>`s this phase introduces.

## Color

Palette unchanged from Phases 1/2 — the indigo-tinted neutral system + one destructive red + `success`/`warning`/`info` `StatusBadge` tones already defined in `app/globals.css`. No new hue introduced for the Kanban board.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `oklch(1 0 0)` ≈ `#FFFFFF` (`--background`) | Page background, board column background |
| Secondary (30%) | `oklch(0.97 0 0)` ≈ `#F5F5F5` (`--card` / `--muted` / `--secondary`) | `DataCard` surfaces, column header strip, Dialog background, sidebar |
| Accent (10%) | `oklch(0.45 0.15 265)` ≈ indigo (`--primary`) | Reserved for: the "Criar card" and "Avançar" (when enabled) primary buttons, the "Anexar link" submit button, checked `Checkbox` fill (shipped shadcn default, not restyled), active sidebar nav item ("Board"/"Checklists"), and the default focus ring. **Not** used on column headers, `DataCard` surfaces, or the package rollup badge (that badge uses `StatusBadge` tone `info`, a lighter accent-family wash — see below). |
| Destructive | `oklch(0.577 0.245 27.325)` ≈ `#DC4C3F` (`--destructive`) | Reserved for: "Forçar avanço" `AlertDialogAction` (destructive variant), "Remover" on a Drive attachment, "Remover" on a checklist-template item row, and the override audit badge (`StatusBadge` tone `danger`, "Avanço forçado"). No other destructive-toned element this phase. |

Accent reserved for: "Criar card" / "Avançar" (enabled) / "Anexar link" primary buttons + checked checkbox fill + active sidebar item + default focus ring — nothing else. `StatusBadge` tones (`success`/`warning`/`info`/`danger`/`neutral`) are a separate, already-established soft-wash system (10% opacity fills per `status-badge.tsx`) used for all status/count communication (checklist progress, package rollup, override marker, column counts) and are not counted against the 10% accent budget — same precedent as Phase 1/2's status pills.
