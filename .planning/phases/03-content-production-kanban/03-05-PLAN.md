## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `forceAdvanceOverride` | `cardId` is attacker-controlled and the action performs a privileged gate bypass; it is directly callable without the Admin UI |
| Server Action → Postgres | The audit insert and the stage update are two separate round-trips with no transaction available |
| Admin UI → cross-client data | `/admin/cards` reads every client's cards; scoping depends entirely on `is_admin()` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-24 | Elevation of Privilege | A PM calling `forceAdvanceOverride` directly to bypass their own client's gate | mitigate | App-layer `profile.role === "admin" && status === "approved"` check before any write, plus `card_checklist_overrides_admin_insert` rejecting the audit insert at the RLS layer — proved by pgTAP assertion 3, which shows a PM cannot insert an override even on their OWN assigned client |
| T-03-25 | Repudiation | A card advancing past unchecked items with no record of who did it | mitigate | The audit row is inserted BEFORE the stage update and its error aborts the action, so a partial failure yields a record with no advance rather than an advance with no record; `overridden_by` comes from `auth.getUser()`, never from a client argument |
| T-03-26 | Repudiation | A second code path that force-advances without logging | mitigate | `forceAdvanceOverride` is the only exported function permitted to advance FORWARD out of `revisao_interna` with unchecked items; `advanceStage` accepts no bypass parameter and `moveCard` rejects the same forward transition through `evaluateMove`.
